1. Резюме

Направление трансформации подтверждено, а обоснование перешло от деклараций к фактам. С момента первого ревью документация получила: формальную модель смены источника истины (Gate A/B/C/D), диаграммы развёртывания (легаси / целевая программа / будущее вне скоупа), полный сравнительный анализ 4 архитектурных альтернатив (было — только выводы без обоснования), первые эмпирические измерения на реальном Blazor Server MVP 0.1 (не только на легаси и не только в теории): реакция на 100 конкурентных сессий и на пакетное изменение 200 000 записей в легаси, — и, в этом обновлении, честную методологию оценки трудозатрат (факт по MVP 0.0–0.1 отделён от оценок моделей, единый непроверенный множитель ускорения ИИ убран), явный перечень новых сценариев недоступности прикладного слоя (§2.1) и описанную семантику партиального успеха Excel-загрузки. Решение по-прежнему следует одобрять как направление и программу пилотирования — но зона неопределённости, требующая факта, а не плана, заметно сузилась.

2. Проверка заявления об ускорении с ИИ

Ключевая претензия снята: единая итоговая цифра плана («9 человеко-лет → ~2,5 человеко-года, ~3,6×») убрана из документа вместе с арифметической нестыковкой (630 дн / 220 = 2,86, а не «~2,5»), которая эту цифру и породила. Вместо неё: (1) зафиксирован факт только по пройденным стадиям MVP 0.0–0.1 — 85 чел.-дней (ретроспективная оценка Ивана по итогам выполнения, явно помечена как не залогированное время, а не как измеренный факт в строгом смысле); (2) колонки моделей («ИИ без ИИ» / «ИИ с ИИ») остаются оценками, не выдаются за факт; (3) введён отдельный пункт бэклога (0.4а) — калибровка по категориям работ (анализ, разработка нового, тираж, тестирование, ОПЭ/критический путь) вместо единого множителя на весь план.
Что ещё не сделано: калибровка 0.4а — это план, а не факт; предметная калибровка пока есть неявно только для одной категории (тираж read-only по фреймворку, см. §2 «ИИ-агенты», разброс моделей ~10%). Итоговая пересчитанная цифра по всему плану по-прежнему отсутствует — но теперь это осознанно отложено до накопления факта по пилотам 0.5–0.7, а не скрытая арифметическая нестыковка, выданная за готовый прогноз.

3. Сильные стороны решения

Снижение распределённости

  • Теперь подкреплено диаграммой развёртывания: 5 легаси-служб + RabbitMQ + Elastic → один процесс `.NET Blazor` на той же ВМ.

Возврат логики в приложение

  • Явно задокументировано единственное осознанное исключение (SP-трансформация интеграций) — не скрытый пробел, а обоснованный trade-off.

Типизированная модель данных

  • Судьба ~40 справочников вне скоупа описана; полный сравнительный анализ SQL-only vs SQL+Elastic теперь в документе (14 критериев), а не одна строка вывода.

Поэтапная миграция с формальным откатом

  • Gate C с протоколом отката; полный сравнительный анализ Strangler Fig vs Big Bang (13 критериев) и Build vs Buy (16 критериев) — ранее отсутствовали вовсе.

Честная методология оценки трудозатрат

  • Единый непроверенный множитель ускорения ИИ (и лежавшая в его основе арифметическая ошибка) убран; факт отделён от плана; калибровка по категориям работ вместо одной цифры на весь проект (0.4а).

Явный реестр новых сценариев недоступности

  • Инфраструктурная доступность 98,5% наследуется от легаси, но добавочные, специфичные для нового прикладного слоя сценарии (обрыв circuit при recycle app pool, отказ sync-воркера, стопор write-toggle, ошибка URL Rewrite) перечислены и смягчены явно, а не оставлены молчаливым допущением (§2.1).

9. Финальная рекомендация

Направление трансформации и программа пилотирования рекомендуются к согласованию с более сильной доказательной базой, чем на предыдущем этапе. Два из трёх ключевых условий одобрения (целостность миграции — Gate-модель; производительность — первые факты на Blazor Server) теперь частично подтверждены не только планом, но и измерением. Третье (фактический коэффициент ускорения ИИ) остаётся неподтверждённым, но сам документ больше не выдаёт единую непроверенную цифру за факт: заявление «~3,6×» и лежавшая в его основе арифметическая нестыковка убраны, вместо них — факт только по MVP 0.0–0.1 (85 чел.-дней) и явный план раздельной калибровки по категориям работ (0.4а). Массовый перенос ~55 read-only справочников и тираж записи по доменам по-прежнему следует разрешать только после завершения полного протокола §6.9 на целевом объёме и первых фактов пилотов записи (MVP 0.5–0.7).

Управленческая рекомендация: до появления факта калибровки 0.4а не закладывать в бюджет единый коэффициент ускорения программы — планировать по диапазону, ориентируясь на уже подтверждённую факту категорию (тираж read-only, разброс моделей ~10%) как на нижнюю границу правдоподобия, и относиться к любой более высокой сквозной цифре как к неподтверждённой гипотезе до пересчёта.
