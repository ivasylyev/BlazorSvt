# Постановка: API СВТ для Атласа — пилот (только чтение)

Статус: утверждено и реализовано (пилот 0.3.2.1–0.3.2.6).

## 1. Цель

Атлас — единая точка входа для пользователей поверх СВТ, CRM, SAP и других систем. В пилоте пользователь Атласа ищет и смотрит записи любых справочников СВТ, открывает карточку, выгружает Excel и подбирает одну ставку умным подбором.

СВТ остаётся единственным источником данных и правил. Атлас не хранит копий и не является интеграционной шиной: обмены СВТ с CRM и SAP идут как сейчас, напрямую, мимо Атласа.

Интерфейс СВТ 2.0 остаётся для части ролей (администратор, владельцы данных). Массовый пользователь работает в Атласе. В перспективе возможен полный переход пользователей в Атлас.

## 2. Границы

**В скоупе:**

- чтение всех **зарегистрированных** справочников СВТ 2.0: список, карточка, описание полей;
- синхронная выгрузка в Excel;
- умный подбор ставки;
- доступ через доверенную служебную учётную запись;
- доработка журналирования;
- OpenAPI и Swagger UI;
- ревизия правил и документации проекта.

**Вне скоупа (отдельные задачи):**

- запись, загрузка файлов;
- асинхронная выгрузка с хранением файлов;
- ограничения частоты и объёма запросов;
- подбор пачкой;
- MCP-обёртка для ИИ-агентов (в пилоте только заложена возможность);
- новые операторы фильтров;
- изменение `v2.GetBlazorGridData`.

**Расширение без смены контракта.** Когда для справочника появится редактор или загрузчик, к тем же ресурсам добавятся `POST`, `PUT` и `uploads`. Атлас увидит это в `capabilities`. Остальной контракт не меняется.

## 3. Операции

| Операция | Назначение |
|---|---|
| `GET /api/v1/catalogs` | Справочники, доступные пользователю: код, название RU/EN, домен, `capabilities` |
| `GET /api/v1/catalogs/{c}/schema` | Поля: имя, тип, название, допустимые операторы, сортируемость, значения перечислений, ссылка на справочник для полей-ссылок, поля периода действия, ключ записи |
| `POST /api/v1/catalogs/{c}/items/search` | Страница записей |
| `GET /api/v1/catalogs/{c}/items/{id}` | Карточка записи |
| `POST /api/v1/catalogs/{c}/export` | Excel сразу в ответе, потоком. Параметр `kind`: `short` — колонки грида, `full` — поля карточки. Колонки полные, без пользовательских настроек |
| `POST /api/v1/rates/smart-lookup` | Одна ставка по дереву умного подбора |

**Ключ записи** — свойство DTO, помеченное `[GridColumn(IsEntityKey = true)]`. Он же указывается в `schema` и используется в адресе карточки.

**Тело поиска:**

- `filters` — список условий, объединяются только через И;
- `sort` — одно поле и направление;
- `page`;
- `pageSize` — от 1 до 1000, больше — ошибка 400;
- `asOf` — дата, только для справочников с полями периода действия;
- `includeArchived` — по умолчанию `false`.

**Ответ поиска:**

- `items` — записи;
- `totalCount` — общее число найденных;
- `dataAsOf` — время последней синхронизации снимка из `v2.SyncState`.

**Справочники в API.** Каждый модуль регистрирует свой справочник при старте одной строкой. Маршруты создаются в цикле по этим регистрациям, у каждого справочника свой тип ответа в OpenAPI. Обработчик общий и идёт через `IGridDataService` и `v2.GetBlazorGridData`. Всё, что есть в СВТ 2.0, попадает в API автоматически.

## 4. Фильтры

### 4.1. Что поддерживает `v2.GetBlazorGridData` сейчас

| Тип поля | Как работает | Что процедура игнорирует без ошибки |
|---|---|---|
| Текст | Любой оператор превращается в полнотекстовый поиск по началу слова (`"значение*"`). Регистр не учитывается. Кавычки, `*`, скобки, `&`, `\|` вырезаются | Значения короче 3 символов. Сам оператор: «равно», «начинается с», «не содержит» и другие работают как «содержит слово, начинающееся с» |
| Число, ключ, дата | `=`, `<>`, `<`, `<=`, `>`, `>=` | Неизвестный оператор, неразбираемое значение, дату вне диапазона DATETIME |
| Флаг | `true` / `false` | Любое другое значение |
| Любой | — | Поле, которого нет в списке разрешённых колонок |

**Сортировка.** Одно поле, всегда досортировка по `[Id]`, поэтому порядок однозначный. Без сортировки — по `[Id]`. При этом процедура разрешает сортировку по любой колонке таблицы, а не только по разрешённым.

**Размер страницы.** Верхнего предела в процедуре нет.

**Пусто и не пусто.** Не поддерживается.

### 4.2. Что проверяет API

Проверки выполняются по описанию справочника, до вызова процедуры:

- **Текст.** Разрешён только оператор `contains`. Значение после очистки короче 3 символов — ошибка 400. Смысл оператора («по началу слова, без учёта регистра») описывается в `schema` и OpenAPI.
- **Числа, ключи, даты.** Операторы `eq`, `ne`, `lt`, `le`, `gt`, `ge`. Неразбираемое значение — ошибка 400.
- **Флаги.** Оператор `eq`.
- **Прочие ошибки 400.** Поле не из `schema`, сортировка по несортируемому полю, `pageSize` больше 1000.
- **`asOf`.** Превращается в два условия: «дата начала ≤ дата» и «дата окончания ≥ дата». При реализации проверить, бывает ли в снимках пустая дата окончания: такие записи выпадут, а `GetBlazorGridData` в этой задаче не меняется.

## 5. Умный подбор ставки

Эталон — процедура `CalcTransportRateCRM` в том виде, как она работает на проде.

### 5.1. Вход

- Обязательные поля: коды узла отправления, узла назначения, продукта, типа транспорта 3 уровня и валюты.
- `date` — необязательна, по умолчанию сегодня по времени сервера (Москва).
- `profile` — профиль приоритетов типов ставок. Необязателен, по умолчанию «Импорт в CRM». Позже у Атласа может появиться свой профиль.

### 5.2. Алгоритм

1. По входу определяются вид транспорта, регион назначения (через `Region.RegionCodePlanning`) и транспортная группа (`ProductGroup`).
2. Шаги 1–8 для основного узла отправления:

| Шаг | Что поднято до более общего |
|---|---|
| 1 | Ничего, точное совпадение |
| 2 | Продукт до транспортной группы |
| 3 | Узел назначения до региона |
| 4 | Регион и транспортная группа |
| 5 | Тип транспорта до вида |
| 6 | Вид и транспортная группа |
| 7 | Регион и вид |
| 8 | Регион, транспортная группа и вид |

3. Шаги 9–16 — те же 8 шагов для дополнительных узлов отправления из справочника «Организации DPO». Они проверяются после всех шагов основного узла.
4. Кандидаты — активные средневзвешенные ставки 3 уровня, действующие на `date`, с типом ставки из профиля для данного вида транспорта.
5. Порядок выбора одной ставки: приоритет типа ставки, затем номер шага, затем близость к средней по группе одинаковых ставок, затем большая ставка.
6. Пересчёт в запрошенную валюту — легаси-функцией `fnCurrencyRateConversion` по курсу на `date`. Если курса нет — ошибка 422 `currency_rate_missing`.

### 5.3. Ответ

- `found` — найдено или нет;
- ставка: ключ, значение в запрошенной валюте, исходное значение и валюта, курс и его дата, загрузка транспорта, период действия, тип ставки и приоритет, фактический тип транспорта;
- пояснение подбора: номер шага, что поднято, заменён ли узел отправления и на какой, текстовое описание.

«Ставка не найдена» — ответ 200 с `found = false`. Ошибки входа — 400 со списком по полям.

### 5.4. Источники данных (исключение только для подбора)

- Ставки берутся из снимка `v2.AverageRateLevel3`.
- Регионы, продукты, транспортные группы, типы транспорта 3 уровня, организации DPO, приоритеты типов ставок и курсы валют читаются из легаси-представлений.
- Это записанный технический долг. При переносе каждого из этих справочников подбор переключается на его снимок.

### 5.5. Реализация

- Отдельный модуль подбора.
- Кандидаты читаются одним запросом.
- Ранжирование — чистая функция в C#, общая для будущих заявок на расчёт и CRM. Логика в SQL не переносится.
- Тип и вид транспорта сравниваются явно, по отдельности. Если это даст расхождение с процедурой, расхождение фиксируется как исправление ошибки.

## 6. Доступ

- `/api` работает под той же Windows-аутентификацией, что и весь сайт.
- Служебная учётная запись Атласа на время пилота входит в AD-группу администраторов СВТ.
- **Список доверенных клиентов** хранится в настройках и допускает несколько значений. На дев-стенде — служебная учётка и учётки разработчиков, на проде — только служебная.
- Учётная запись не из списка получает 403 на весь `/api`. Это защищает и от вызова API из браузера обычного пользователя (подделка межсайтового запроса, CSRF).
- Пользователь передаётся заголовком `X-On-Behalf-Of: DOMAIN\user` на всех операциях. Без заголовка — 400 `on_behalf_of_required`.
- Права считаются **только** по ролям указанного пользователя (`dbo.User` / `dbo.UserRole`), как в Blazor. Права служебной учётки не добавляются.
- Пользователь не заведён в СВТ — 403 `user_not_registered`. Ролей нет — 403 `user_has_no_roles`. Отказ `IAccessGuard` — 403 `access_denied`.
- Пилотные пользователи — те же, что работают в легаси СВТ.
- Неизвестный код справочника или отсутствующая запись — 404 (`catalog_not_found` / `item_not_found`). В пилоте посправочникового ACL нет: любая роль даёт чтение всех зарегистрированных справочников.

## 7. Журналирование

- Для `/api`: `UserLogin` — конечный пользователь, `ApiClient` — служебная учётка, `Channel = Api`.
- В Blazor-сессиях `UserLogin` и `ShortCorrelationId` не меняются, добавляется только `Channel = Blazor`.
- Входящий `X-Correlation-ID` принимается и возвращается в ответе.
- По каждому вызову пишутся: операция, справочник, число строк, длительность, код ответа. Тело запроса целиком в журнал не пишется.

## 8. Контракт

### 8.1. Формат данных

- JSON, имена полей в camelCase.
- Дата без времени — `yyyy-MM-dd`, дата со временем — ISO 8601 в UTC с `Z`.
- Перечисления — строковыми кодами.
- Денежные значения — числом с объявленной точностью.
- Пустое значение — `null`, поле не пропускается.
- Пары полей RU/EN отдаются как есть. `Accept-Language` (`ru` / `en`) переводит только названия полей и тексты ошибок.

### 8.2. DTO

Те же, что у грида и карточки. Их состав заморожен тестами контракта.

### 8.3. Ошибки

ProblemDetails со стабильным кодом ошибки (`catalog_not_found`, `page_size_exceeded`, `invalid_filter`, `rate_not_found`, `currency_rate_missing` и т.п.) и `traceId`.

### 8.4. Кеширование и прочее

- Ответы с данными — `Cache-Control: no-store`. Для `catalogs` и `schema` — `ETag`.
- Ответы сжимаются (gzip / brotli).
- При обрыве соединения клиентом SQL-запрос и выгрузка отменяются.
- Во время перезапуска пула приложений клиент получает 503 и повторяет запрос с паузой.

### 8.5. Версии и совместимость

- Версия `v1` в адресе.
- Добавление поля — совместимое изменение. Удаление или переименование — только в `v2`.
- Требование к клиенту Атласа: незнакомые поля игнорируются.
- Заголовок `Sunset` для `v1` со значением 01.01.2099.

### 8.6. OpenAPI и Swagger

- Спецификация генерируется встроенными средствами .NET 9.
- У каждой операции стабильный `operationId` и описание на обычном языке, с примерами запросов и ответов. Это задел под будущую MCP-обёртку.
- Swagger UI включается настройкой. На стендах разработки и теста — включён, на проде — по решению при выпуске.
- `openapi.json` хранится в репозитории. CI падает на несовместимом изменении контракта.

## 9. Тесты и приёмка

- **Unit:**
  - преобразование фильтров API в `GridQuery` и все отказы из раздела 4.2;
  - ранжирование умного подбора по каждой ветке дерева;
  - разбор доверенного клиента и пользователя.
- **Интеграционные:**
  - операции API через `WebApplicationFactory` с тестовым обработчиком аутентификации;
  - схема доступа: права только пользователя; без заголовка — 400; недоверенная учётка — 403.
- **Сверка подбора.** Read-only тест по истории запросов из `dbo.TransportRateCRM`: новая реализация против `CalcTransportRateCRM`. Расхождения разбираются по одному, с учётом отставания снимка от легаси.
- **Тест контракта OpenAPI.**
- **Новый справочник** без регистрации в API не проходит тесты.

## 11. Задачи в бэклог и дорожную карту

1. **Ограничения:** частота запросов на клиента, одновременные выгрузки, предел строк выгрузки.
2. **Асинхронная выгрузка:** хранение файлов на диске виртуалки, статус операции в таблице БД, срок хранения, очистка.
3. **Доступ после пилота:** отдельная роль «API-клиент» вместо группы администраторов. Переход на токены корпоративного провайдера учётных записей (OIDC), если он есть у Атласа.
4. **Фильтры:** оператор «одно из списка» — в гриде и в API.
5. **Фильтры:** операторы «пусто» и «не пусто» — в гриде и в API.
6. **Текстовые операторы грида:** «равно», «начинается с», «не содержит» и другие сейчас работают как «содержит». Реализовать их или убрать из интерфейса.
7. **Умный подбор:** перевести на снимки при переносе справочников-источников.
8. **Подбор пачкой.**
9. **MCP-обёртка** поверх API.
10. **Согласования:**
    - класс данных и отдача ставок в контур Атласа;
    - сетевой доступ из контейнерного контура к виртуалке СВТ;
    - HTTPS-сертификат, которому доверяет Java-клиент;
    - стенд СВТ и данные для интеграции с Атласом;
    - владелец контракта и порядок его изменения;
    - решение по Swagger UI на проде.

## 12. Принятые риски пилота

- Синхронная выгрузка без предела строк в общем процессе с Blazor: нагрузка на память и соединения. Атласу нужен большой таймаут чтения.
- Нет ограничения частоты запросов: нагрузка от Атласа может влиять на пользователей СВТ 2.0.
- Служебная учётка с правами администратора: при её компрометации можно действовать от имени любого пользователя.
- Подбор читает живые легаси-представления, а ставки — снимок с отставанием. Сразу после правки ответ может ненадолго отличаться от ответа CRM.
- Аудита изменений полей нет до MVP 1.0. Для операций чтения не критично.

## 13. Вопросы к команде Атласа

1. Как Java-клиент в контейнере проходит Windows-аутентификацию служебной учёткой: Kerberos с keytab или NTLM?
2. Подтверждение формата логина `DOMAIN\user` и требования «игнорировать незнакомые поля».
3. Есть ли у Атласа корпоративный провайдер учётных записей (OIDC)? Ответ нужен для перехода на токены после пилота.
