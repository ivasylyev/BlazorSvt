1. Контекст

После детального разбора бэклога выявлено: около половины инцидентов связаны с некорректными бизнес-правилами, которые не соответствуют текущим бизнес-процессам. Вторая половина — техника и архитектура. Исправление архитектуры необходимо, но недостаточно для гарантии корректных данных пользователям и смежным системам.

ЧастьЧто этоЧем лечится
Требования · ~50% Система принимает данные, которые бизнес считает ошибкой: требования устарели или непонятны Исправление некорректных данных в системе и повторная отправка в интеграции. Полечили только случаи, с которыми столкнулись. Случаи регулярно повторяются из-за неактуальных и неполных бизнес-правил. Необходимо провести пересмотр имеющихся бизнес-правил и сформулировать требования для их переработки.
Техника и архитектура · ~50% Подвисания или сбои при загрузке, падение интеграций Добавление железа и настройка SQL Server, переработка структуры базы данных, оптимизация запросов, доработка интеграций с мониторингом

Что закрыли и чего не закрыли

Сделано

Техника, которую можно было выжать без смены архитектуры

  • Добавили мощность и настроили SQL Server — первая волна ускорения.
  • Оптимизировали код запросов, проверили на стенде как прод, выложили.
  • Подключили вторую линию к разбору инцидентов. Интеграции — у Коряйкина, срок 31.10.
Не подтвердилось

Эволюционно «распутать» иерархию таблиц

Гипотеза упростить структуру хранения в текущем SQL Server не дала эффекта. Фильтр «только неархивные» тоже. Корневая модель данных на месте. Это предел текущего контура, не отложенная задача из бэклога.

Решение: дальнейшую оптимизацию запросов не финансируем. Оценка оставшегося прироста — около 18%, не доказано, 2–3 недели работы. На гипотезах реальный эффект уже оказывался меньше обещанного. Ресурсы несоразмерны. Хвост вне этого решения: довыложить расчёт валют.

Почему одной техники мало

Около половины инцидентов — не скорость, а данные, которые система принимает, а бизнес считает ошибкой. Правила устарели. Точечный ремонт повторяющихся случаев не закрывает причину. Пока зафиксировано 34 нарушенных правила. Примеры:

В работе

Описать идеальный процесс СВТ по методологии Атласа

СВТ стоит в начале эталонного процесса. Сначала идеальный процесс, затем интервью и актуальные правила: что система должна отсекать, а что проводить. С техникой Ш2 не смешиваем. Ответственная — Е. Подоплелова.

Не сейчас

Целевой проект

Только когда есть предел техники (уже есть) и актуальные требования. Тогда оценка L3, ресурс и бюджет. Не открываем трансформацию «чтобы дожать ещё 18%».

СВТ — ведение тарифов, маршрутов, лидтаймов и ограничений. Материал владельца продукта. Цифры Ш2 — после массовой загрузки на проде; база «4 мин» — после быстрой победы по SQL, не III квартал.
