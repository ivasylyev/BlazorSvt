# Промпт: собрать пакет внедрения из executive-версии эталонного процесса

> Вход — один готовый executive-документ целевого процесса (кольцо: шаги + сквозные механизмы + агенты/контроли/данные, метод «кольца», уже согласован). Выход — один zip-архив: план, приложение с образом результата, шаблоны владельцам шагов, промпт для аналитика логов (Промпт 2а — копируется в архив целиком, не переписывается). Роли в пакете обезличены — не подставлять реальные ФИО нигде, только должности.

---

## 0. Роли (использовать везде вместо имён)

Ровно две действующие роли, без исключений:

- **Менеджер процесса** — бизнес-сторона: владеет содержанием процесса, курирует владельцев отдельных шагов, разблокирует бизнес-вопросы.
- **Лидер цифровизации от ИТ** — ИТ-сторона: ведёт разработку системы **и** сам готовит/проводит анализ логов (процесс-/таск-майнинг, по промпту 2а) для предзаполнения шаблонов. Оба трека — на одной роли, это нормально: они слабо пересекаются по времени (майнинг — в начале, разработка — потом).

Если в исходном executive-документе встречаются реальные фамилии (авторы разделов, ответственные) — переносить их роль, но не имя: «раздел подготовлен менеджером процесса», не «Ивановым».

---

## 1. Вход: что должно быть в executive-документе

Проверить перед стартом, что источник содержит:

- Легенда нотации — коды шагов/правил/агентов/контролей/данных и их значения (в примере ниже — Ш/П/А/К/Д, у другого процесса буквы и слова могут быть другие — извлекать те, что фактически есть в документе, не подставлять этот набор по умолчанию).
- Кольцевая карта: список шагов по порядку, список сквозных механизмов.
- Таблица «как сейчас → сложность → целевая модель» — по каждому шагу и каждому механизму.
- Приложения: реестр агентов (с привязкой агента к шагу), реестр контролей (с привязкой к шагу), реестр данных (с привязкой к шагу/механизму).

Если чего-то из списка нет — не выдумывать, а явно сообщить, какого раздела не хватает, и продолжать с тем, что есть, отметив пробел в плане (раздел 4.1 ниже).

---

## 2. Извлечение перед сборкой

Построить внутри себя (не выводить пользователю как отдельный артефакт, использовать как рабочую структуру для шагов 3–7):

- Список шагов с кодом, названием, целевой моделью (дословно из источника).
- Для каждого шага — список агентов, которые на нём работают (код + название).
- Для каждого шага — диапазон/список кодов контролей и данных, которые к нему относятся (по приложениям источника).
- Список сквозных механизмов отдельно от шагов — они не имеют одного «владельца-шага», их читают несколько шагов сразу.
- Если у процесса есть профильная ветка (как ЗХП у закупок — вариант того же кольца с своим источником потребности и частью специфичных агентов/контролей) — выделить её как отдельный «профильный» раздел, дельта поверх обычных шагов, а не как ещё один параллельный набор шагов.
- Если в источнике есть раздел про интеграции/системы — выделить отдельно: он не разбирается логами (см. правило в 5.3).

---

## 3. Структура выходного архива

Один zip, внутри — четыре папки и один короткий README в корне архива (не вне его):

```
Пакет_от_эталона_к_разработке.zip
├── README.md
├── 1_План/
│   └── План_внедрения.docx
├── 2_Образ_результата/
│   └── Приложение_А_Образ_результата_по_шагам.docx
├── 3_Шаблоны_владельцам/
│   ├── <Шаг-1>.docx
│   ├── <Шаг-2>.docx
│   ├── … (по одному на каждый шаг источника)
│   ├── <Сквозные_механизмы>.docx
│   ├── <Профильная_ветка>.docx        (если есть в источнике)
│   └── <Интеграции>.docx               (если есть в источнике)
└── 4_Инструменты_аналитика/
    ├── 00_Индекс.md
    └── Промпт_2а_Обработка_логов.md      (единый инструмент на весь пакет данных, копируется целиком)
```

README.md в корне — не инструкция «что делать людям» (это внутри плана), а чисто навигационный: что в какой папке, в каком порядке открывать. 3–5 предложений, не больше.

---

## 4. Часть 1 — План внедрения (`1_План/`)

Один документ, разделы:

**4.1. Образ результата.** Что считается готовым результатом всей программы (не по годам — по проверяемым вехам: пакет данных для майнинга подтверждён → черновики готовы → шаги заполнены владельцами → сверка пройдена → первые постановки в разработку → первый работающий результат). Если на шаге 1 источника не хватало разделов — здесь же явно отметить, что план в этой части неполон и почему.

**4.2. План действий по ролям — обязательный раздел, не общими словами.** Две таблицы, «Когда → Что делает», по каждой из двух ролей раздела 0 отдельно:

- *Менеджер процесса*: участие в стартовой коммуникации о программе; при наличии в источнике «сложного»/детально проработанного шага — операционное владение именно им (пилот); разблокировка бизнес-вопросов остальных владельцев; участие в приёмке результатов сверки; подпись регламента перехода от ручного контроля к автономному решению агента.
- *Лидер цифровизации от ИТ*: подготовка и подтверждение готовности пакета данных для майнинга; прогон промпта анализа логов (Промпт 2а, раздел 4 архива) и рассылка черновиков владельцам; заказ технических доступов; приёмка заполненных шаблонов; старт и ведение разработки; релизный ритм.

**4.3. Пакеты и владельцы.** Таблица: пакет (шаг/механизм/профиль/интеграции) → что покрывает → оперативный владелец (плейсхолдер `[должность/ФИО по месту]`) → куратор со стороны менеджера процесса. Не придумывать реальные имена — только структура таблицы, заполняется на месте.

**4.4. Сводный план по неделям.** Недели считать от нуля: неделя 0 — организационный старт (коммуникация, назначение владельцев, подтверждение пакета данных, доступы); далее — заполнение черновиков аналитиком, заполнение шаблонов владельцами, сверка, генерация постановок на разработку, старт разработки. Явно выделить: интеграционная разведка и любые согласования с смежными функциями (безопасность, юридическая функция, если релевантно процессу) стартуют с недели 0, а не когда-то позже — это типовая ошибка более ранней версии подобных планов, избегать её.

**4.5. Как встроен майнинг в заполнение (если применимо к процессу).** Явной таблицей: артефакт шаблона → что даёт анализ логов (Промпт 2а) → куда именно в шаблоне это попадает. Если процесс не оставляет цифровых следов (нет систем/логов) — прямо написать, что майнинг-часть неприменима, и шаблоны заполняются без черновиков, с нуля.

**4.6. Реестр артефактов, риски и меры.** Кратко: что уже готово (источник, этот план), что создаётся (черновики, заполненные шаблоны), что в итоге (постановки на разработку). Риски — общего типа для такой программы (конфликт интересов у тех, чью работу описывают под автоматизацию; шаблоны как мнения, а не факты, если заполняются без майнинга; риск позднего обнаружения интеграционных ограничений; риск заполнения четырьмя владельцами четырёх версий одного и того же сквозного правила) — и мера на каждый в этом же плане.

---

## 5. Часть 2 — Образ результата (`2_Образ_результата/`)

Один документ: по каждому шагу — код, название, целевая модель дословно из источника (не пересказывать своими словами, не сокращать формулировки про пороги/условия). Короткое пояснение в шапке: держать открытым рядом с шаблоном при заполнении «как сейчас» — разница между этим текстом и текущим положением дел и есть содержание работы.

---

## 6. Часть 3 — Шаблоны владельцам (`3_Шаблоны_владельцам/`)

По одному файлу на каждый пакет (обычный шаг / сквозные механизмы одним файлом / профильная ветка, если есть / интеграции, если есть). **Не разбивать на отдельные шаблоны по типу артефакта** (паспорт отдельно, данные отдельно, агенты отдельно) — один файл на пакет включает всё, что нужно этому владельцу:

- Паспорт: границы, как исполняется сегодня, объёмы, боли — с пометками-подсказками в квадратных скобках, не готовыми ответами.
- Реестр релевантных данных этого пакета — строки-заготовки с колонками код/название/источник сегодня/способ доступа/пример значения.
- Карточка на каждого агента этого пакета: текущий аналог, триггер и вход, логика решения, границы и HITL-точка, событие-результат, примеры (типовые + граничные + HITL-случаи), метрика качества.
- Реестр релевантных контролей этого пакета — код/что проверяет/условие/где проверяется сегодня.

**Обязательный блок в начале каждого файла, простыми словами, без канцелярита**, объясняющий разделение ролей: анализ логов по этому пакету делает **лидер цифровизации от ИТ**, не владелец; результат приходит отдельным файлом-черновиком; владелец переносит и правит, не пишет с нуля; «не знаю / уточнить у [роль]» — валидный ответ, пустое поле — нет.

**В шаблонах владельцам не должно быть ни одного промпта.** Это главное правило части 6 — если промпт анализа оказался в файле для владельца, задача пакета сделана неверно.

Для пакета «интеграции» (если применимо) — тот же блок в начале должен честно объяснять, что это не майнинг-центричный пакет: заполняется по документации и интервью с техвладельцами систем, а не по логам.

---

## 7. Часть 4 — Инструменты аналитика (`4_Инструменты_аналитика/`)

Папка содержит ровно два файла — не по одному на пакет, как раньше, а один универсальный инструмент плюс индекс к нему.

**7.1. `Промпт_2а_Обработка_логов.md`.** Копируется в архив дословно, без пересказа и без сокращений — это готовый промпт, а не материал для переписывания. Он один на весь пакет данных, а не на отдельный шаг: внутри уже есть весь порядок работы (приёмка сырых архивов → единая событийная база → связность и трейсы → раскладка по шагам кольца и черновики) и все правила анонимности, пометок достоверности и проверок. Дублировать это здесь не нужно.

**7.2. `00_Индекс.md`.** Три части:

- Таблица «пакет → есть ли логи (да / нет / частично) → на основании какого шага источника собран».
- **Структура черновика** — единая для всех пакетов, не переписывается заново под каждый: паспорт / реестр релевантных данных / карточка на каждого агента / реестр релевантных контролей (дословно раздел 6 этого промпта). Промпт 2а на этапе «Раскладка» (его раздел 4.3) запрашивает «структуру, которую требует промпт этого пакета» — этой структурой и служит данный раздел индекса, один общий, а не N файлов с повторяющимся текстом.
- Порядок работы: единая событийная база строится один раз по всему массиву логов (этапы 1–3 промпта 2а — не по пакету за раз, раскладка по пакетам начинается только на этапе 4); дальше промпт 2а прогоняется по каждому пакету поверх уже готовой базы и создаёт черновик `Черновик_<пакет>.md`; черновик уходит владельцу по маршруту раздела 6 этого промпта; после того как владелец заполнит шаблон — по той же базе прогоняется сверка (промпт 2а, раздел 5), без пересборки базы с нуля.

Если у процесса нет ни одного пакета с цифровыми следами — папка всё равно создаётся, но индекс прямо говорит: «логов нет ни по одному пакету», и файл промпта 2а в архив не копируется.

---

## 8. Упаковка — обязательное финальное действие

Все документы части 4–7 создаются как файлы на диске в соответствующих папках, README — в корне. После того как все файлы собраны — упаковать всё дерево целиком в один zip-архив. **Ничего не оставлять отдельным файлом рядом с архивом** — ни инструкцию, ни план, ни README: если что-то не в архиве, значит сборка не завершена.

---

## 9. Финальная проверка перед выдачей

- В архиве ровно четыре папки плюс README в корне, никакой плоской россыпи файлов.
- В папке 4 — ровно два файла: `00_Индекс.md` и `Промпт_2а_Обработка_логов.md`, скопированный целиком без изменений (или явная пометка в индексе, что логов нет и файл промпта не копировался).
- Ни в одном файле папки 3 не встречается слово «промпт» или блок кода с инструкцией для ИИ — это признак того, что материал для аналитика попал не в ту папку.
- Каждый шаблон папки 3 содержит блок про разделение ролей (раздел 6 этого промпта) — без него владелец не поймёт, почему в шаблоне пустые поля соседствуют с обещанием черновика.
- Ни одна реальная фамилия не встречается нигде в архиве — только «менеджер процесса» и «лидер цифровизации от ИТ» (плюс родовые плейсхолдеры `[должность/ФИО]` там, где место конкретного человека).
- Число файлов в папке 3 совпадает с числом пакетов, извлечённых на шаге 2 (обычные шаги + сквозные механизмы одним файлом + профильная ветка, если есть + интеграции, если есть).
- Целостность архива проверена программно (открывается, ни один файл не повреждён), а не на глаз.
