1. Картина процесса

1.1. Модель

СВТ ведёт: ставки, паритеты, маршруты, плечи и лидтаймы, складские ограничения, матрицу каналов.

Каждое изменение проходит полный цикл — шаги Ш1…Ш9: получение данных, обработка, передача потребителям и контроль. Детали шагов для каждого домена описаны в разделе 2.

  • Ш1 Получение данных — СВТ получает данные из систем-источников. Данные, отсутствующие в системах-источниках, человек вводит вручную. Формат авто-ставок СВТ приводится в соответствие с форматом ставок Логинета.
  • Ш2 Проверка данных — СВТ проверяет данные по одним и тем же правилам, откуда бы они ни пришли. Данные делятся на три потока: строки без нарушений сразу идут на Ш4 и не ждут Ш3; строки с отклонениями ждут утверждения на Ш3; строки с ошибками заносятся в лог и исключаются из дальнейшей обработки.
  • Ш3 Утверждение исключений — человек решает, пропустить или отвергнуть строку с отклонениями, которую проверка посчитала подозрительной. Это единственный шаг, на котором движение данных может остановиться, и только для строк с исключениями.
  • Ш4 Расчёт производных значений — СВТ рассчитывает дефлированные ставки типов, кроме бизнес-плановых и спотовых; средневзвешенные, бизнес-плановые и спотовые ставки; паритеты; лидтаймы. Бизнес-плановые и спотовые ставки дефлятором не умножаются.
  • Ш5 Ввод в действие — новые данные начинают действовать с указанной даты, прежние уходят в архив. Справочник паритетов накопительный, старые записи не архивируются. Складские ограничения в архив не списываются и на одну дату не пересекаются.
  • Ш6 Передача потребителям — СВТ сама отдаёт действующие значения системам-потребителям. Вступившее в силу значение уходит с задержкой порядка 5 минут; ночью идёт полная синхронизация с потребителями.
  • Ш7 Контроль полноты — СВТ показывает, каких данных не хватает, и пользователь их дозаводит или даёт сигнал источнику: так начинается новый цикл.
  • Ш8 Контроль целостности — СВТ проверяет корректность и консистентность существующих данных. Ошибки исправляет администратор ИТ новым циклом с Ш1 для изменённых данных.
  • Ш9 Сверка план-факт и сигнал источникам — СВТ сравнивает действующие значения с фактом и сообщает о расхождении системе-источнику.

На Ш7, Ш8 и Ш9 цикл не останавливается: человек разбирает нехватку, ошибки и расхождения, а данные тем временем продолжают действовать и уходить потребителям.

Шаги опираются на единые проверки, реестр исключений, журнал загрузок, отчёт о полноте и расхождениях, передачу потребителям онлайн и ночную синхронизацию.

1.2. Источники

Основной путь — автоматический обмен. Ручной ввод и ручная загрузка для всех потоков, кроме мультимодальных перевозок, — дополнительный путь, его сокращают. Для мультимодальных перевозок ручной файл — основной путь только на первом этапе, дальше он дополнительный.

  • Логинет. Отдаёт тендерные ставки авто с номинациями, фактические ставки и фактическую цену спотового аукциона. Модель данных авто-ставок Логинета, около 30 столбцов, переносится в СВТ.
  • ATI через Озеро данных (где хранятся данные — пробел). Отдаёт индикативные ставки авто.
  • Умная логистика (как получать данные — пробел, контакт — Мария Бамбина). Система, в которой запрашивают индикативные ставки авто. В Озере данных её нет. Есть API и договор. Сначала посмотреть, как выглядит система, затем договориться о получении данных.
  • Калькулятор НХТК (как получать данные — пробел, контакт — Настя Сироткина). Отдаёт железнодорожные ставки и расстояния.
  • Картографический сервис (какой именно — пробел). Отдаёт расстояние между отправлением и назначением плеча для авто по России.
  • Система отслеживания машин (как получать данные — пробел, контакт — Иван Фролов). Отдельная система со своим индексом, не Логинет и не Озеро данных. Отдаёт фактический лидтайм авто.
  • Внешние порталы. Teustat, MSC, Феско, CMA, Maersk, Drewry и другие. Отдают данные для паритетов. Teustat — через интерфейс (как получать данные — пробел). Данные иностранных порталов, возможно, придётся загружать через Excel.
  • Почта (согласовать с бизнесом — пробел). Еженедельный файл складских ограничений. Образец файла получен; как автоматизировать его разбор, ещё нужно изучить. Пока агент не подключён, файл разбирает алгоритм в коде. Агент — по правилу второго этапа в пункте 1.3.
  • Ручной ввод бизнеса. Договорные ставки, дефляторы и период факта для бизнес-плана, коэффициенты распутицы, ручная корректировка бизнес-плановых ставок.
  • АСВ и ERP. Отдают контрагентов, узлы, продукты, курсы и склады.

1.3. Обработка данных

Данные в СВТ приходят в виде независимых друг от друга строк. Пришедшие данные проходят одинаковые проверки вне зависимости от источника (интеграции, ручного ввода и загрузки файла).

Список проверок составляется совместно с бизнесом и реализуется в коде.

Агент подключается вторым этапом, только если бизнес признает это целесообразным. Когда правила меняются часто и данных много, агент нужен: бизнес сам меняет правила, а данные обрабатываются автоматически. Когда правила меняются редко и данных мало, агент не внедряется: правила меняет техническая поддержка в коде системы, данные вносит бизнес вручную.

  • Жёсткая проверка отклоняет строку: например, у ставки не указана стоимость или загрузка транспортного средства;
  • Мягкая проверка отправляет её человеку на утверждение, только если возникло отклонение: например, стоимость на 50% выше прежней.

Строки без отклонений идут дальше, не дожидаясь разбора отклонений.

Новое значение действует с указанной даты, прежнее уходит в архив. Паритеты копятся без архивации. Складские ограничения на одну дату не пересекаются.

СВТ рассчитывает:

  • ставки, кроме бизнес-плановых и спотовых, — с коэффициентами дефлирования; ставки авто — ещё и с коэффициентами распутицы;
  • бизнес-плановые ставки — из других типов ставок, без дефлятора;
  • спотовые ставки — из других типов ставок с корректировкой по факту, без дефлятора;
  • средневзвешенные ставки — из всех типов ставок. Расчёт идёт в различной гранулярности, усредняя по контрагентам, по регионам и т. д.;
  • паритеты;
  • лидтаймы авто — с корректировкой по факту;
  • лидтаймы ЖД.

Подробности — в шаге Ш4 процессов «Ставки», «Паритеты» и «Маршруты, плечи и лидтаймы».

После этого данные уходят потребителям почти онлайн после вступления в силу, а также выполняется полная ночная синхронизация.

1.4. Сервисы

Кроме ведения модели, в СВТ есть сервисы.

Сервис заявок. По заявке на расчёт ставки СВТ подбирает ставку из модели, то есть из справочника средневзвешенных ставок или паритетов при помощи «умного подбора». Заявка бывает на обычную ставку и на массовую. Заявки не входят в модель: это запрос к данным модели, а не данные. Это отдельный порядок работы со своими шагами, а не шаг кольца. пробел Модуль заявок переработать: упростить порядок работы с заявкой и связать её со справочником паритетов.

Сервис синхронизации ставок. На одном направлении СВТ заменяет устаревшую ставку группы продуктов актуальной ставкой другой группы: подставляется значение той группы, которая уже обновлена. Правила синхронизации расширяются на большее число продуктов и становятся настраиваемыми. Если подставилась не та ставка, правку правила вносит владелец продукта. Результат синхронизации — новое значение ставки, оно проходит проверки, вводится в действие и уходит потребителям, как любое другое.

Сервис подбора для CRM. Когда в CRM подбирают тариф, CRM отправляет запрос в СВТ, и умный подбор срабатывает сразу. Если ставка найдена, она уходит в CRM и используется там. Если не найдена, пользователь в CRM сам нажимает кнопку «Запросить тариф СВТ»: так запрос остаётся осознанным, а одинаковые повторные запросы не превращаются в заявки. Заявка с предзаполненными полями автоматически уходит в СВТ, пользователь получает уведомление, что ответ придёт на почту. Переходить в СВТ и подтверждать заявку ему не нужно.

Цель — 95% заявок закрываются автоматически, 5% — действительно новые ставки. Если подбор ставку не нашёл, она проходит шаги Ш1–Ш6 процесса «Ставки» и становится значением справочника для всех, а не только для инициатора. пробел Правила умного подбора обсуждаются отдельно.

1.5. Потребители

СВТ — мастер-система по ставкам, паритетам, маршрутам, плечам и лидтаймам, складским ограничениям и матрице каналов. Системы-потребители получают данные через автоматическую интеграцию без ручного вмешательства: почти онлайн после вступления значения в силу и полной ночной синхронизацией. Планирование читает маршруты как схему доставки, логистика — чтобы обеспечить мощности.

  • CRM и E-Com. Получают средневзвешенную ставку, подобранную умным подбором. Нужна для расчёта цены клиенту. Если ставка ниже рынка, Сибуру приходится доплачивать за перевозку. Если выше, Сибур рискует потерять клиента.
  • ССП. Получает ставки вместе с привязанными к ним маршрутами, плечами и лидтаймами. Также получает складские ограничения. Нужны, чтобы добавить логистику в цену планируемого спроса: затем спрос уходит в ЦБД. пробел Нужны ли данные СВТ в ССП ещё и для составления ППР — уточнить.
  • ЦБД. Получает ставки и лидтаймы в горизонте 15 месяцев. Лидтаймы нужны, чтобы оценить срок заморозки рабочего капитала. Ставки нужны для оптимизационной модели: она выбирает клиентов и поставки так, чтобы максимизировать EBITDA компании.
  • Маркетинг. Получает паритеты. Забирает данные из Озера данных и строит на них витрину. Своей системы и подключения к шине у маркетинга нет. Нужны для ценообразования, расчёта доходности продаж продукта по заводам и оценки конкурентов на смежных рынках.
  • ЕСД, программа Оптимакрос. Получает ставки, лидтаймы, параметры складов и складские ограничения. Они нужны для календарного планирования, диспетчеризации потоков и учёта загрузки складов.
  • ЕСД SI (что получает ЕСД, а что ЕСД SI, — уточнить у бизнеса, пробел). Получает складские ограничения вместе с ЕСД и КПО. Нужны, чтобы проверять исполнимость плана и использовать закупленные мощности.
  • КПО (уточнить у бизнеса — пробел). Получает складские ограничения, плановый лидтайм доставки и матрицу каналов: квоты, ставки и плановые лидтаймы уходят через программу Оптимакрос. Нужны, чтобы учитывать ограничения отправки железнодорожным и автомобильным транспортом по каналам и направлениям. Рейтинг складов получает из MLS.
  • MLS. Получает ставки 3 уровня из Озера данных. Они нужны, чтобы рассчитать рейтинг складов: с какого склада выгоднее отгружать продукт клиентам региона. MLS — модуль СВТ гипотеза.
  • SAP ERP. Получает маршруты и лидтаймы. По маршруту создаёт разнарядки на отгрузку: без маршрута отгрузка клиенту не выполняется. По лидтайму планирует отгрузки — нормативные плановые даты.
  • SAP TMS. Получает ставки с номинацией для мультимодальных перевозок. Ставки нужны, чтобы заказывать контейнерные поезда и вести мультимодальные перевозки.
  • Озеро данных. Получает сырые данные. Нужны для дашбордов и Контрольной среды.
  • Атлас. Получает все данные, по которым СВТ — мастер-система: ставки, паритеты, маршруты, плечи и лидтаймы, складские ограничения и матрицу каналов. Через интерфейс Атласа выполняются действия этого процесса. Значение — на дату, своей копии Атлас не ведёт.

Так заводят уникальные данные, которых нет ни в одной системе, вручную дополняют или корректируют то, что пришло автоматически, и вносят ставку при подписании ДС. Этот путь проходит те же проверки Ш2.
  • Журнал загрузок. Каждая загрузка пишется в журнал: что, когда, откуда и куда загружено, сколько строк прошло, ушло в исключения и отклонено. Ключевой пользователь видит журнал почти в реальном времени, сверяет загрузки с утверждённым графиком и раньше замечает ошибку, например, пакет в сто раз меньше обычного. На журнале строится аналитика.
  • Справочные данные. Контрагенты, узлы, продукты, курсы и склады приходят из АСВ НСИ и ERP, как сегодня. Склады — WarehouseASVERP и WarehouseERP. Продукты приходят по внешней интеграции; это вспомогательный справочник для ставок и паритетов, отдельного процесса у него нет.

Дефлированные ставкиПрогнозные ставки с коэффициентом дефлятора. Считаются от действующей ставки типа, который не является бизнес-плановым и не является спотовым.
ДефляторКоэффициенты к ставкам, кроме бизнес-плановых и спотовых. Коэффициенты вводит бизнес вручную.
ПлечоТранспортное плечо. Состоит из двух узлов, отправления и назначения, или из трёх: отправление, промежуточный узел и назначение. Промежуточный узел используется, как правило, в мультимодальных перевозках на экспорт и обычно является пограничным переходом.
МаршрутТранспортный маршрут. Состоит из одного плеча или из нескольких плеч, соединённых последовательно.
Складские ограниченияЁмкость склада для разных видов продукции, пропускная способность погрузочно-разгрузочных работ и тариф склада. Задаются на интервал времени. На одну дату интервалы одного склада не пересекаются: это отклоняет жёсткая проверка на загрузке и находит контроль целостности. Прежняя запись хранится со своим интервалом и в архив не списывается. СВТ отдаёт ограничения оптимизатору, в том числе стоимость хранения. Склад, к которому относится ограничение, СВТ собирает из АСВ НСИ и SAP ERP. Человек задаёт у склада только график работы. В ограничении, кроме ёмкости, пропускной способности и тарифа, есть затраты фикс на хранение за месяц.
Матрица каналовВосемь сущностей для календарного планирования: завод отгрузки, узел отправления, направление (зона узлов назначения), направление-канал, завод-канал и три уровня квот (по узлам отправления, по направлениям-каналам, по заводам-каналам). Направление-канал связывает тыловой терминал (необязательно), погранпереход и направление. Завод-канал связывает завод с направлением-каналом; ему соответствуют несколько маршрутов — по узлам назначения. Квоты — помесячно, с единицей измерения КП, КТК, КВ или Авто; авто и КП не суммируются. Потребитель — КПО через Оптимакрос.
Заявка на расчёт ставкиЗаявка конечного пользователя на подбор ставки транспортировки заданной продукции по заданному маршруту определённым типом транспорта, обычная или массовая. Это сервис СВТ, а не данные модели. Ставку подбирает система. Если подбор неоднозначен, заявку обрабатывают вручную.
ЛидтаймНормативный срок перевозки.
ИИ-агентПрограмма второго этапа. Подключается, только если бизнес признает это целесообразным: правила меняются часто и данных много, тогда бизнес сам меняет правила, а данные обрабатываются автоматически. Когда правила меняются редко и данных мало, агент не внедряется: правила меняет техническая поддержка в коде, данные вносит бизнес вручную.
