# I. План трансформации СВТ

## 1. Контекст и цели

### 1.1. Бизнес-контекст

- СВТ — MDM по управлению логистическими маршрутами, тарифами и складскими ограничениями.
- Масштаб: ~100 справочников; 10–100 полей; до ~2 млн записей (цель новой системы — до 10 млн); пакетная загрузка до 30 тыс. строк.
- **Скоуп переноса:** ~60 используемых справочников; **~40 вне скоупа** (не используются бизнесом).
- Пользователи: ~300 на чтение, ~10 на запись.
- Интеграции: ~30 потоков.
- Языки UI: ru / en.

### 1.1а. Группы справочников и группы пользователей

Скоуп ~60 справочников делится на группы по бизнес-домену. 4 группы пользователей работают
с записью в свои домены независимо (без пересечения по бизнес-функционалу) — это позволяет
переносить запись (редакторы и загрузчики) вертикально по доменам и флипать SoT инкрементально,
домен за доменом (см. §2а).

| Группа справочников | ~Кол-во | Группа пользователей | Комментарий |
|---|---|---|---|
| Ставки | ~10 | A | Максимально нагружены и нестабильны в легаси; влияют на бизнес-планирование компании — переносятся первыми |
| Маршруты | ~5 | B | Независимая группа пользователей |
| Продукты | ~5 | A (та же, что Ставки) | Ниже приоритет, чем Ставки, хотя те же пользователи |
| Склады и ограничения | ~7 | D | Независимая группа пользователей |
| Матрица каналов | ~5 | C | Независимая группа пользователей; данные могут частично пересекаться со Складами, но не пользователи |
| Интеграция с ЦБД | ~5 | A (та же, что Ставки) | Ниже приоритет, чем Ставки и Продукты |
| Вспомогательные | ~25 | A + B + C + D (используют все) | Переносятся последними — нужна обратная связь всех 4 групп |

Этот же список из 7 доменов — единый канонический справочник, используемый одинаково для критериев
Gate A/B/C/D (§2а), доменной ролевой модели («Редактор {Домен}», раздел 9) и доменного write-toggle
(раздел 10) — чтобы три механизма не расходились в классификации справочников по доменам.

Порядок переноса (единый для справочников только для чтения (read-only) и для вертикального тиража записи):

**Ставки → Маршруты → Продукты → Склады и ограничения → Матрица каналов → Интеграция с ЦБД → Вспомогательные**

### 1.2. Цель трансформации

- Снизить совокупную стоимость владения (TCO).
- Обеспечить масштабируемость объёмов данных и расчётов.
- Устранить архитектурные ограничения легаси, препятствующие развитию.
- Цель — не «чистая архитектура ради стека».

### 1.3. Стратегия

- **Strangler Fig**: поэтапное замещение, общая БД на переходный период, параллельная работа старой и новой систем.
- **SoT = легаси-таблицы до cutover.**
- **Exit dual-run** — волнами (по справочнику/группе): выключение старого UI после сверки и приёмки; запись по-прежнему write-through в легаси-таблицы.
- **Механизм хостинга и переключения UI**: новое приложение — дочернее приложение в том же IIS-сайте,
  что и легаси (не отдельный сайт), с переиспользованием identity/Integrated Security пула приложений IIS (app pool)
  (без кросс-сайтовой авторизации). Переключение между легаси-UI и новым UI постранично/по домену —
  через IIS URL Rewrite. Это техническая реализация «выключения старого UI» в exit dual-run и Gate B
  (см. §2а).
- **SoT flip — инкрементальный, по доменам** (Gate C, см. §2а): каждый домен (Ставки, Маршруты,
  Продукты, Склады и ограничения, Матрица каналов, Интеграция с ЦБД, Вспомогательные) флипается
  независимо, административным решением, сразу после прохождения им Gate A (сверка) и Gate B
  (ОПЭ) — не дожидаясь готовности остальных доменов.
- **Write-through в легаси продолжается для всех флипнутых доменов без ограничения по времени** —
  вплоть до единого финального демонтажа легаси (Gate D, MVP 2.0). Это даёт возможность отката
  на легаси по любому домену в любой момент до Gate D без потери данных.
- **Gate D (физический демонтаж легаси)** — один раз, глобально, после того как ВСЕ домены
  (включая Вспомогательные) прошли Gate C; необратим.

### 2.1. Новые (не унаследованные от легаси-инфраструктуры) сценарии недоступности

Контракт доступности 98,5% (см. строку «RTO/RPO» выше) наследуется от общей ВМ/IIS/БД и
покрывает **инфраструктурные** причины простоя (сеть, плановые работы, отказ ВМ) — они
действительно не меняются. Но новый прикладной контур (Blazor Server + watermark-sync + write-toggle) добавляет сценарии недоступности/деградации, которых у легаси не существовало
физически, и которые контракт 98,5% сам по себе не покрывает — они митигируются отдельно:

| Новый сценарий | Почему его не было в легаси | Митигация |
|---|---|---|
| Перезапуск пула приложений IIS (app pool recycle) обрывает все активные интерактивные сессии Blazor (circuit) (пользователь видит «reconnecting…», может потерять несохранённый ввод) | В легаси (Angular + REST) перезапуск пула приложений IIS (app pool) прозрачен — следующий запрос просто чуть медленнее | Явно зафиксировано как известный компромисс Blazor Server; смягчается редким релизным окном (вне рабочего времени) |
| Отказ/зависание воркера синхронизации — грид отстаёт от легаси без явной ошибки для пользователя | Отдельного sync-процесса в легаси не было (одна БД) | `V2SyncEnabled` (kill switch, 5.5) + алерты 5.6/5.6а + подключение алертов к техподдержке (5.6б) |
| Стопор доменного write-toggle из-за бага нового кода — блокирует запись по конкретному домену | В легаси такой единой точки отказа для записи по домену не было | Доменный (не глобальный) `V2WriteEnabled_{Домен}` — ограничивает blast radius одним доменом (§2, строка «Обратная запись») |
| Некорректная конфигурация IIS URL Rewrite при переключении легаси-UI ↔ новый UI в период dual-run | Механизма переключения UI не существовало — был один UI | Обязательная проверка URL Rewrite перед первым Gate B каждого домена (2.7) |

Ни один из этих сценариев не отменяет наследование 98,5% на уровне инфраструктуры — они
дополняют его как явно поднятые и отдельно смягчаемые риски нового прикладного слоя, а не как
молчаливое допущение «то же самое, что и раньше».

## 2а. Критерии перехода между стадиями SoT (Gate A/B/C/D)

Единица перехода — домен из §1.1а (Ставки, Маршруты, Продукты, Склады и ограничения,
Матрица каналов, Интеграция с ЦБД, Вспомогательные). Флип выполняется независимо по каждому
домену; Вспомогательные — последними, т.к. используются всеми 4 группами пользователей.

**Gate A — техническая сверка домена.** Не требует разработчика; может идти параллельно
у нескольких доменов одновременно (в т.ч. параллельно с Gate B другого домена).

- 0 расхождений категории «потеря/искажение данных» и ≤0,1% расхождений категории
  «ожидаемый lag» за последние 14 календарных дней подряд (автосверка по кодам, см. §2, строка sync).
  Задержка отражения жёсткого удаления архивной/просроченной записи в пределах окна
  reconciliation относится к категории «ожидаемый lag», не к «потере данных» (см. §2, строка sync).
- p95 отставания курсора watermark ≤ 5 минут за период наблюдения.
- Нагрузочный тест на фактическом объёме домена: p95/p99 не хуже легаси.
- Нет открытых дефектов уровня critical/blocker по домену за последние 14 дней.

**Gate B — ОПЭ (опытно-промышленная эксплуатация) домена.** Нужен дежурный разработчик —
не более одного домена одновременно в Gate B; Gate A других доменов может идти параллельно.

- Длительность работы пользователей домена исключительно в новом UI (легаси-UI домена отключён —
  технически через IIS URL Rewrite, см. §1.3; write-through в легаси продолжается) — адаптивная:
  по умолчанию 4 недели; может быть сокращена
  до минимум 2 недель, если за истёкший период 0 расхождений категории «потеря данных» по
  автосверке и reconciliation (см. §2, строка sync) и 0 инцидентов P1/P2 — иначе остаётся 4 недели
  (продление сверх 4 недель — по решению того же состава, что подписывает Gate C, при наличии
  открытых вопросов).
- 0 инцидентов P1 (потеря/искажение мастер-данных), ≤2 инцидентов P2 за период, все закрыты
  с зафиксированной причиной, без повторов.
- Для доменов с расчётами (Ставки, позже — заявки) — сверка итоговых сумм с легаси в пределах
  допустимой погрешности, согласованной с бизнес-владельцем.
- Приёмка ОПЭ подписана бизнес-владельцем домена (для Вспомогательных — представителями
  всех 4 групп пользователей).

**Gate C — SoT flip домена.** Административное решение, обратимое.

- Триггер: Gate B пройден для домена.
- Действие: новый контур официально объявляется источником истины для домена; легаси-UI
  домена остаётся выключенным (уже сделано в Gate B); write-through в легаси-таблицы
  ПРОДОЛЖАЕТСЯ без изменений.
- Оформляется протоколом «SoT Flip Decision Record»: дата, домен, кто подписал (архитектор +
  владелец продукта домена + представитель эксплуатации), ссылка на результаты Gate A/B.
- Rollback: в любой момент до Gate D — реактивация легаси-UI и признание легаси источником
  истины для домена по решению того же состава; данные не теряются, т.к. легаси не отставал
  (write-through не прерывался).

**Gate C+ — точечная ретирация write-through (опционально, до глобального Gate D).** Применимо
только к таблицам/справочникам, исключительным для одного домена (не используются другими,
ещё не флипнувшими доменами — проверяется по перечню общих источников синхронизации и
каскадным FK, см. раздел 5). Не применимо к общим сущностям (узлы/регионы/страны и т.п.,
группа «Вспомогательные»), которые обслуживают несколько доменов одновременно.

- Триггер: Gate C пройден для домена; прошёл период наблюдения без инцидентов P1 (ориентир —
  не менее 6 месяцев после Gate C, согласуется индивидуально с бизнес-владельцем и архитектором).
- Действие: остановка write-through только для исключительно-доменных таблиц; связанные
  легаси-объекты выводятся из эксплуатации отдельно от Gate D.
- Решение принимается индивидуально по домену/набору таблиц, не является обязательным шагом —
  применяется там, где нужно ощутимо сократить суммарную стоимость/длительность dual-run.
- Не отменяет и не ускоряет Gate D: общие сущности и общая легаси-инфраструктура
  (Front/GOD-сервис/Elastic/RabbitMQ), обслуживающие ещё не флипнувшие домены, продолжают
  жить до Gate D.

**Gate D — финальный демонтаж легаси.** Один раз, глобально, MVP 2.0, необратимо.

- Триггер: ВСЕ домены, включая Вспомогательные, прошли Gate C.
- Действие: остановка write-through, рефакторинг и удаление легаси-артефактов, вывод
  Front/Elastic/RabbitMQ/GOD-сервиса из эксплуатации (см. раздел 19 бэклога).
- Rollback не предусмотрен — единственная необратимая точка всего плана.

**Пилоты (MVP 0.5/0.6) через Gate A/B/C не проходят** — их задача проверить фреймворк на одной
сущности («Транспортные плечи»), а не флипнуть домен. Флип домена «Маршруты» (включая
пилотную сущность) происходит позже, в MVP 0.7, вместе с остальными ~4 справочниками группы.

## 2б. Отложенная митигация рисков (условия условного архитектурного одобрения)

**Статус согласования, на которое претендует документация:** условное одобрение
направления трансформации и программы пилотирования — **не** безусловное закрытие
всех нефункциональных требований (NFR) и не разрешение массового тиража / контура записи «как есть».

**Принцип.** Жёлтые зоны повторного архитектурного ревью (architecture review)
(`docs/architecture/review-current-state.html`, условия 3–7) — не скрытые пробелы,
а **осознанный остаточный риск (residual risk)** с владельцем, сроком (Gate / MVP) и проверяемым
критерием «стало зелёным». Документация не выдаёт план за факт: закрытие условия —
либо **артефакт** (анализ/согласование), либо **исполнение** (код/CI/замер/drill).

Краткая формулировка для пакета ревью — `reference.md` §6.9.
Полный текст документных митигаций (тип A) — **приложения ниже в этом же §2б**
(не отдельные файлы): удобнее для человека-ревьюера.

**Что одобряется сейчас (при принятии условий ниже):**
- направление: модульный монолит Blazor Server + MS SQL FTS, поэтапная замена (Strangler Fig), CQRS,
  SoT = легаси до cutover, Gate A/B/C/D;
- продолжение read-only dual-run и развитие каркаса в рамках уже сделанного MVP 0.1;
- план работ и реестр отложенных митигаций как обязательная часть программы.

**Что явно не одобряется «вперёд» этим же решением:**
- старт массового тиража ~55 read-only (раздел 7 / MVP 0.2) — до закрытия D-PERF
  (минимум 6.9.9) и D-ARCH (7.0.5);
- пилот записи / загрузчик (MVP 0.5–0.6) — до закрытия D-SEC-RO (0.5.7) и наличия
  черновиков D-SEC-TM / D-SEC-SOD / D-DATA-MIG (приложения §2б; формальное согласование ИБ —
  по D-SEC-RO и вехе раздела 9);

### Приложение D-DATA-MIG — совместимые миграции схемы и откат

> Статус: **черновик** (митигация D-DATA-MIG).  
> Принять командой **до старта MVP 0.5** (пилот записи).

#### Контекст dual-run

На переходный период одновременно живут:

- легаси-таблицы (SoT до Gate C домена);
- схема `v2.*` (snapshot, `SyncState`, будущий outbox аудита);
- write-through из нового контура **в легаси** (с MVP 0.5).

Откат приложения ≠ откат данных. Restore БД — общий (легаси + `v2.*`) на одну точку времени
(§2, RTO/RPO).

#### Принципы расширения/сжатия схемы (expand/contract)

1. **Не ломать** читателей легаси и новый read-контур одним релизом.
2. Любое breaking-изменение колонки/таблицы — в два+ релиза: expand → migrate → contract.
3. Скрипты `SqlScripts/` идемпотентны или версионированы так, чтобы повторный накат на среду
   был безопасен (уже принятая практика publish SQL).
4. Изменения легаси-схемы, нужные только новому контуру, согласовывать отдельно: легаси остаётся
   SoT и обслуживает старый UI до Gate B/C.

#### Чеклист релиза read-only (текущая фаза)

- [ ] DDL только `v2.*` / programmability чтения
- [ ] Sync курсоры переживают рестарт (`SyncState`)

### 6.9. Ранний нагрузочный PoC (после MVP 0.1, до массового тиража в MVP 0.2)

**Оборудование (текущее, то же — для целевой архитектуры этой программы, см. reference.md §4.2):**
сервер приложений — 8 ядер / 32 ГБ (Windows Server 2016, IIS); сервер БД — 4 ядра (MS SQL
Server 2016), отдельная ВМ.

**Предварительные факты (получены на пилотных справочниках MVP 0.1 — Ставки, Ср. ставки и др.,
до формального прогона 6.9.1–6.9.14 на целевом объёме данных):**

- **Интерактивная нагрузка / память circuit'а.** Профиль: 100 Blazor-сессий открыли самую тяжёлую
  карточку (грид + детальная карточка на ~100 полей в сложной иерархии, справочник «Ставки»),
  из них 2 случайные сессии/сек выполняют лёгкое действие (фильтрация, пагинация) — остальные
  «висят» открытыми без активности. Результат на сервере приложений: CPU в среднем 3%, прирост памяти
  IIS ≈150 МБ на 100 сессий (~1,5 МБ/circuit). Это соответствует сценарию **6.9.2** (конкурентное
  чтение), но без записи/синхронизации.
- **Массовое изменение в легаси (аналог сценария 6.9.6, вдвое больше плановой планки 100К).**
  Изменено 200 000 записей ставок в легаси; `V2SyncEnabled` активен. Watermark-sync полностью
  обработал изменения и отразил их в снапшоте за **30 сек** — запас ×10 к критерию Gate A
  (p95 лага ≤5 мин, см. §2а) и попадает в интервал одного цикла (90 с) без накопления отставания.
  На сервере приложений (Blazor/IIS) прирост CPU/памяти во время синхронизации — **<1%** (в пределах
  погрешности измерения). На SQL Server (4 ядра) — среднее CPU **≈15%** на время цикла синхронизации
  (т.е. ~0,6 ядра из 4 заняты; ~3,4 ядра остаются свободными для конкурентных read-запросов).
- **Вывод 1 — подтверждение CQRS-изоляции.** То, что сервер приложений почти не почувствовал обработку
  200К изменений (<1% против 3% фоновой интерактивной нагрузки), а вся стоимость легла на SQL
  Server, — прямое эмпирическое подтверждение архитектурного расчёта на разделение read/write

  ресурсы сервера приложений; единственная точка потенциальной конкуренции — SQL Server, и там она
  измерена (15% из 4 ядер) и выглядит умеренной.
- **Вывод 2 — не хватает совместного прогона.** Два теста выше проводились **раздельно**

- **Не закрыто:** объём данных при этих тестах — фактический текущий объём пилотных

## 9. Реализовать ролевую модель → MVP 0.4

Легаси-модель (Админ / Единое окно / Инициатор / Читатель) согласована с ИБ в 2019 г. для одного
домена (Ставки). При расширении скоупа до 7 доменов (§1.1а) роль «Единое окно» даёт кросс-доменную
запись — нарушение минимальные привилегии (least privilege). Read-only bridging до этого раздела (MVP 0.1–0.3: любая роль `dbo.Role` даёт read всех выложенных справочников и отчётов; Windows Auth + сверка `User`/`UserRole` с прямыми AD-группами `DOMAIN\Group`) — принятое решение без
инкрементального ИБ-риска: новая система не даёт больше прав, чем легаси, для read-only и отчётов.

На уровне БД разграничения нет (Integrated Security, общая учётка управляемой службы (MSA) app pool на тесте/проде,
унаследовано от легаси и согласовано с ИБ ранее; см. §2, строка «Роли и сопоставление с группами
AD») — проверка прав в прикладном слое (9.4) является единственным, а не одним из, рубежом
контроля доступа.

- [ ] 9.1. Инвентаризировать легаси-модель «как есть»: что реально может каждая роль (Админ /
      Единое окно / Инициатор / Читатель), перечень справочников-исключений (интеграционные ~10,
      системные служебные типа TypeRate — правки требуют доработки кода)
- [ ] 9.1а. Спроектировать новую доменную ролевую модель: read — универсальный для всех ролей (как
      сейчас); write — доменные роли «Редактор {Домен}» 1:1 с группами §1.1а (Ставки / Маршруты /
      Продукты / Склады и ограничения / Матрица каналов / Интеграция с ЦБД); «Админ» остаётся
      глобальным суперюзером без доменного разделения (IT/поддержка); обработка заявок — отдельное
      кросс-доменное право «оператор заявок», не привязанное к доменной роли редактора;

- [ ] 9.1б. Перенести фиксированные ограничения легаси в новую модель: интеграционные справочники и

## 16. Реализовать аудит изменений данных → MVP 1.0

До этого этапа аудит на уровне полей отсутствует; риск принят.

Механизм — **Transactional Outbox** (по образцу уже работающего в проекте паттерна
`SnapshotSyncScheduler`/`IV2SyncFeatureToggle`), не наивный fire-and-forget async: наивная
асинхронная запись (без предварительной durable-стадии) создаёт окно, в котором падение/рестарт
процесса (в т.ч. штатный IIS app pool recycle) между `persist` и отложенной записью аудита тихо
теряет запись — без какого-либо следа, что она вообще должна была быть. Это подрывает саму цель
аудита (доверие к расследованию, см. §2, строка «Наблюдаемость»). Брокер сообщений не используется
(см. §2, строка «Отказ от брокера»).

# III. Оценка трудоёмкости

Проверенный факт (ретроспективная оценка Ивана по итогам выполнения, не залогированное время) есть
пока только по MVP 0.0–0.1: **85** чел.-дней — см. таблицу §3 (ч. I), колонка «Факт».  
Колонки «ИИ без ИИ» / «ИИ с ИИ» (**1990** / **960** чел.-дней, **~9** / **~4** чел.-года суммарно
по всему плану) остаются оценками моделей, не фактом. Единый коэффициент ускорения ИИ на весь план
не публикуется — признан недостаточно надёжным для architecture review: реальное ускорение сильно
разнится по типам работ (подтверждённый тираж read-only vs неоткалиброванная логика записи и
ОПЭ-критический путь, см. §2, строка «ИИ-агенты»). Итоговая оценка трудоёмкости всего плана с
раздельными коэффициентами по категориям работ будет дана после калибровки — см. новый раздел
бэклога 0.4а.
