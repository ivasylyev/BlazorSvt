# I. План трансформации СВТ

## 1. Контекст и цели

### 1.1. Бизнес-контекст

- СВТ — MDM по управлению логистическими маршрутами, тарифами и складскими ограничениями.
- Масштаб: ~100 справочников; 10–100 полей; до ~2 млн записей (цель новой системы — до 10 млн); пакетная загрузка до 30 тыс. строк.
- Пользователи: ~300 на чтение, ~10 на запись.
- Интеграции: ~30 потоков.
- Языки UI: ru / en.

### 1.2. Цель трансформации

- Снизить стоимость разработки и сопровождения (TCO).
- Обеспечить масштабируемость объёмов данных и расчётов.
- Устранить архитектурные ограничения легаси, препятствующие развитию.
- Цель — не «чистая архитектура ради стека».

### 1.3. Стратегия

- **Strangler Fig**: поэтапное замещение, общая БД на переходный период, параллельная работа старой и новой систем.
- Отключение легаси — по частям.

---

## 2. Принятые архитектурные решения

| Решение | Содержание |
|---------|------------|
| Архитектурный стиль | Модульный монолит с вертикальными срезами `Modules/{Entity}/` |
| Стратегия трансформации | Strangler Fig, общая БД на переходный период |
| Стек | .NET Blazor Server + MS SQL |
| Данные и поиск | MS SQL — единственный источник истины (индексы + Full-Text Search) |
| Логика | В прикладном коде C#, не в SP/SQL Agent |
| Модель данных | Типизированные таблицы, constraints, не метамодель |
| Чтение / запись | CQRS; единый command-side для редактора и загрузчика |
| Обратная синхронизация в легаси | На переходной период запись из нового контура обновляет данные легаси, чтобы обе системы оставались согласованными |
| Оркестрация интеграций | Внешние адаптеры и сервис интеграции не меняются. В скоупе — перенос оркестрации из SQL Agent и отчёты по ошибкам потоков |
| Заявки на расчёт ставки | Легаси-заявки бизнес-потребностям не соответствуют. Реализуем заново отдельный модуль с простым workflow (не BPM) |

**Порядок переноса справочников (группы):**  
Ставки → Продукты → Склады и ограничения → Матрица каналов → Интеграция с ЦБД → Вспомогательные.

Без универсального конструктора: каждый дашборд — алгоритм агрегации в коде. Ориентир ~10 дашбордов. Агрегаты кешируются в отдельных таблицах; UI — таблицы + диаграммы с drill-down; для списка записей — по возможности существующие гриды.

- 18.1. Провести аналитику и сбор требований по дашбордам
- 18.2. Сделать каркас модуля дашбордов (регистрация, меню, права, маршруты)
- 18.3. Реализовать движок расчёта и обновления агрегатов (по расписанию и/или после изменений) с записью в cache-таблицы
- 18.4. Подготовить SQL-структуру кеш-таблиц под дашборды
- 18.5. Сделать UI: диаграммы, сводные таблицы, drill-down в грид/карточку справочника
- 18.6. Провести пилот одного дашборда end-to-end (агрегация → кеш → UI → drill-down)
- 18.7. Развернуть остальные дашборды (~10) по тому же шаблону
- 18.8. Добавить контроль актуальности кеша и времени пересчёта
- 18.9. Провести внутреннее функциональное тестирование
- 18.10. Исправить дефекты, выявленные в ходе тестирования
- 18.11. Провести UAT
- 18.12. Выполнить релиз на продуктив

**Критерий:** ~10 дашбордов открываются быстро из кеша, с drill-down до исходных записей; логика каждого дашборда реализована в коде.

## 19. Модернизировать интеграции → MVP 1.2

Integration-сервис также пишет ошибки в БД — для них тоже отчёты.

- 19.4. Сохранить семантику входящих и исходящих потоков (mdm_integ ↔️ mdm)
- 19.5. Унифицировать фиксацию ошибок оркестрации, SP-перекладки и Integration-сервиса
- 19.6. Сделать общий шаблон отчёта по интеграциям (статус, ошибки, флаги, описание, время, объём, drill-down к записям)

- 19.8. Внести минимальные точечные правки легаси только там, где без них нельзя подключить оркестрацию или отчётность

**Критерий:** внешние интеграции работают как раньше; оркестрация управляется из нового контура; ошибки по потокам видны в отчётах.
