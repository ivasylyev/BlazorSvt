## Вехи и оценка трудоёмкости

Оценки в человеко-днях. Три слота: без ИИ (оценка ИИ); с ИИ (оценка ИИ); с ИИ (оценка человеком — только прежние вехи 1 и 2). Поэлементно — в чеклисте [backlog.md](backlog.md). Источник расчёта — `docs/estimation/`.

Каждый домен справочников — одна веха; фазы MVP, ОПЭ и ПЭ — пакеты внутри вехи. Юзкейсы, прототип и демо есть только у домена «Заявки»: это пакеты 5.1–5.3 внутри вехи 5. Номера вех, пакетов и задач перенумерованы 18.11.2026, 26.11.2026 и 27.11.2026 в порядке исполнения; таблицы «старый номер → новый» — `docs/estimation/renumber_map.json` (18.11.2026), `docs/estimation/renumber_map_cut.json` (26.11.2026; вехи 1–63 → 1–34) и `docs/estimation/renumber_map_cut2.json` (27.11.2026; вехи 1–34 → 1–16, слияние доменных вех).

Проверенный факт (ретроспективная оценка Ивана по итогам выполнения, не залогированное время) есть
пока только по прежним вехам 1 и 2, до перенумераций: **85** чел.-дней — колонка «Человек». На вехи 1–16 этот факт не раскладывается: в строках стоит прочерк.

## Домены и группы пользователей

Скоуп 61 справочника делится на группы по бизнес-домену. 4 группы пользователей работают
с записью в свои домены независимо (без пересечения по бизнес-функционалу) — это позволяет
переносить запись (редакторы и загрузчики) вертикально по доменам и флипать SoT инкрементально,
домен за доменом (см. [cutover.md](cutover.md), раздел «Критерии Gate»). Справочники, которые используются только в одном домене (в т.ч.
бывшие «вспомогательные» ставки), остаются в этом домене, а не выносятся в общий.

Состав каждого домена, сложность, работы и приоритеты — в [catalogs-scope.md](catalogs-scope.md).

Порядок вертикального тиража записи:

**Ставки → Паритеты → Маршруты → Продукты → Вспомогательные → Склады и ограничения → Матрица каналов → Интеграция с ЦБД**

У домена «Продукты» редактора и загрузчика нет: справочники читаются, запись домена — API записи (пакет 9.1).

`TransportRequest` и `MassiveRequest` вне скоупа: в СВТ 2.0 не переносятся, история остаётся в легаси. Расчёт ставки — домен «Заявки».

Порядок вех (номер совпадает с очередью; чеклист — [backlog.md](backlog.md)):

**1 → 2 → … → 16**

Порядок вех: «Супер-читатель» (веха 4) идёт перед «Заявками» (веха 5). Проект Атлас в состоянии ожидания (на 27.11.2026), поэтому заявки не идут первыми. Юзкейсы и прототип «Заявок» — аналитика, они не ждут разработки читателя; остальное идёт по очереди номеров. Старт «Заявок» держит пункт 2.5.1 «бизнес утвердил роли» (веха 2; Р-01…Р-19). Проверки ролей в коде — пакет 6.1. До 6.1 заявку создаёт любая роль `dbo.Role`, обрабатывает `Window Users`.

Принцип порядка. Сначала переносятся наиболее критичные домены (вехи 4–9), затем вспомогательные справочники, которые используются в критичных доменах (веха 10), затем стабилизация системы (веха 10), затем оставшиеся домены (вехи 11–13). Если программа остановится после вехи 10, система всё равно приносит пользу.

Юзкейсы, прототип и демо домена «Заявки» (пакеты 5.1–5.3) исполняются до разработки модуля, который они описывают. Утверждение перечня (2.7) — в вехе 2, после плана. Калибровка оценок (6.19) — после пилотов редактора и загрузчика: до них нет статистики факта. Комплект вывода (передача в поддержку, приёмка поддержкой, замер приживаемости) стоит на волне чтения, на заявках, на каждом домене записи и на вспомогательных. Совместный контроль метрик (16.1) исполняется после вывода последнего домена и Gate D не ждёт.


## Критический путь

**Критический путь вех записи (6–13), не сжимаемый ИИ:** Gate A (14 дн, для первого домена не перекрывается ничем) + Gate B (адаптивно 2–4 недели на домен, не более одного домена одновременно, см. [cutover.md](cutover.md), раздел «Критерии Gate») × 8 доменов (7 доменов записи + Вспомогательные в вехе 10) ≈ **16–32 недели (~4–8 месяцев)** только на прохождение gates, независимо от скорости кодогенерации ИИ (доработка следующего домена может идти параллельно с Gate B текущего, но сама последовательность Gate B серийна — критический путь). Трудоёмкость разработки вех записи в человеко-днях ожидает пересчёта после калибровки по категориям работ (см. 6.19) — до калибровки не заявляется как сопоставимая или несопоставимая с этим критическим путём; узкое место программы на вехах записи может оказаться именно ОПЭ (критический путь по календарю), а не скорость написания кода — это будет видно по факту первого флипнувшего домена.
