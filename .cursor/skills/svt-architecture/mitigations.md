#### Границы системы

### Приложение D-SEC-SOD — разделение обязанностей (SoD)

> Статус: **черновик** (митигация D-SEC-SOD).  
> Матрица SoD — до вехи 6; иммутабельность журнала аудита — веха 11.

#### Переходная модель доступа

| Фаза | Кто читает | Кто пишет | Примечание |
|------|------------|-----------|------------|
| веха 2–3, затем 5 | Пользователи с ≥1 ролью из `dbo.Role` | Справочники в новом контуре не пишутся | Паритет с легаси read-only; Windows Auth + `User`/`UserRole` |
| С включения 4, до 6 | Та же роль читает справочники | Заявки: создаёт любая роль `dbo.Role`, обрабатывает `Window Users` | Домен «Заявки», только новый контур. С 6 создание переходит к Р-03, обработка — к Р-06 |
| API (Атлас), веха 5+ | Тот же контингент: роли пользователя из `X-On-Behalf-Of` | Никто (пилот только чтение) | Служебная учётка — только допуск клиента (`Api:TrustedClients`), своих прав в API не даёт |
| вехи 6 | По доменным ролям | «Редактор {Домен}» и др. | Согласование с ИБ до вехи 7 |
| Админ | Глобальный суперюзер | Feature toggles, админка | Отдельный контроль |

Детали ролей — backlog 6.1 и строка «Роли»).

#### Матрица SoD (черновик)

| Роль A | Роль B | Совмещение | Обоснование |
|--------|--------|------------|-------------|
| Редактор {Домен X} | Редактор {Домен Y} | Допускается только явным решением | Снижение радиуса поражения (blast radius); кросс-домен — отдельное право |
| Редактор любого домена | Админ (toggles / URL Rewrite) | **Запрещено** по умолчанию | Разделение изменения данных и изменения контура |
| Р-06 Обработчик заявок | Админ (Р-04) | **Запрещено** | Workflow ≠ инфраструктурный контроль |
| Р-03 Инициатор заявок | Р-02 Администратор домена | По AD-процессу заказчика | Р-03 создаёт заявку и не меняет справочники. Р-07 читает и заявки не создаёт |

> Заполнить фактическими AD-группами заказчика при согласовании вехи 6.

#### Привилегированные действия

| Действие | Кто | Аудит до вехи 11 | Аудит с вехи 11 |
|----------|-----|------------------|----------------|
| `V2SyncEnabled` on/off | Админ / поддержка | Лог приложения + изменение в `vw_FeatureToggle` | + field-level / outbox где применимо |
| `V2WriteEnabled_{Домен}` on/off | Админ / поддержка | То же | То же |
| IIS URL Rewrite (переключение UI) | Инфраструктура | Чеклист Gate B (2.7); изменение конфига IIS | Вне прикладного аудита — runbook |
| Ручной запуск reconciliation / сверки | Поддержка | Лог + алерт | То же |
| Назначение доменных ролей | Админ (админка 6) | Журнал админки (план раздела 9) | + неизменяемый след |
| Persist мастер-данных | Редактор | **Нет** field-audit (принятый риск) | Transactional Outbox, backlog 11.1 |

#### Неизменность журнала (решение — зафиксировать к вехе 11)

Варианты (выбрать один при проектировании раздела 16):

1. Журнал только на добавление (append-only) outbox + запрет UPDATE/DELETE правами приложения (gMSA без DELETE на audit).
2. Периодический hash-chain / контрольная сумма суточных партиций.
3. Выгрузка в архив однократной записи (WORM) по политике ИБ (если потребует ИБ).

До выбора: риск «наивная асинхронная запись без durable-стадии» уже митигирован дизайном Transactional Outbox (строка «Наблюдаемость, сверка данных, аудит изменений»).

**Критерий готовности:** матрица SoD с реальными AD-группами; запрещённые совмещения согласованы с ИБ;
выбран вариант иммутабельности журнала; ссылка из раздела 9.

### Приложение D-DATA-MIG — совместимые миграции схемы и откат

> Статус: **черновик** (митигация D-DATA-MIG).  
> Принять командой **до старта вехи 7** (пилот записи).

#### Контекст dual-run

На переходный период одновременно живут:

- легаси-таблицы (SoT до Gate C домена);
- схема `v2.*` (snapshot, `SyncState`, будущий outbox аудита);
- write-through из нового контура **в легаси** (с вехи 7) и после Gate C, до Gate D.

Откат приложения ≠ откат данных. Restore БД — общий (легаси + `v2.*`) на одну точку времени
(строка «RTO/RPO» в [risks.md](risks.md)).

#### Принципы расширения/сжатия схемы (expand/contract)

1. **Не ломать** читателей легаси и новый read-контур одним релизом.
2. Любое breaking-изменение колонки/таблицы — в два+ релиза: expand → migrate → contract.
3. Скрипты `SqlScripts/` идемпотентны или версионированы так, чтобы повторный накат на среду
   был безопасен (уже принятая практика publish SQL).
4. Изменения легаси-схемы, нужные только новому контуру, согласовывать отдельно: легаси остаётся
   SoT и обслуживает старый UI до Gate B/C.

#### Чеклист релиза read-only (текущая фаза)

- [ ] DDL только `v2.*` / programmability чтения
- [ ] Sync курсоры переживают рестарт (`SyncState`)
- [ ] Smoke после деплоя (2.4)
- [ ] Rollback приложения: предыдущий билд + SQL backward compatible

#### Чеклист релиза write (с вехи 7)

- [ ] Persist пишет в известную легаси-модель; нет скрытых DDL «на лету»
- [ ] Доменный write-toggle проверен (fail-closed)
- [ ] План отката: выключить `V2WriteEnabled_{Домен}` → пользователи на легаси-UI при необходимости
- [ ] Данные, уже записанные write-through, остаются в легаси (откат UI не требует rollback строк)
- [ ] Если менялся контракт идемпотентности — описан ключ повторного применения
- [ ] Миграции `v2.*`, связанные с outbox/аудитом — expand/contract

#### Запрещено без явного протокола архитектурного решения (ADR)

- Удаление/переименование колонок легаси, от которых зависит старый UI, до Gate D.
- Несовместимый с предыдущим билдом контракт snapshot без окна dual-version.
- «Откат данных» точечным DELETE после ошибочного батча без отчёта и процедуры (см. партиальный
  успех batch, 8.2.4).

**Критерий готовности:** принято командой до кодирования persist вехи 7; чеклист write включён
в релизный runbook; ссылка из раздела 10.

### Приложение D-OBS — индикаторы и цели уровня сервиса (SLI/SLO)

> Статус: **черновик** (митигация D-OBS).  
> Единый каркас поверх уже заданных числовых SLO sync. Закрыть таблицу до вехи 7.

Инфраструктурная доступность **98,5%** наследуется от легаси (общая ВМ/IIS/БД).  
Ниже — **прикладные** индикаторы уровня сервиса (SLI) и цели уровня сервиса (SLO) нового контура;
сценарии недоступности — [risks.md](risks.md), раздел «Новые сценарии недоступности».

#### Каталог SLI/SLO

| ID | SLI | SLO (цель) | Источник метрики | Алерт / реакция | Фаза |
|----|-----|------------|------------------|-----------------|------|
| S1 | Доступность UI нового контура (успешные circuit / HTTP) | В рамках общего 98,5% + учёт recycle | IIS / app logs | Релизное окно вне рабочего времени | 2+ |
| S2 | p95 ответа грида (пилот/тираж) | Не хуже легаси на сопоставимом объёме; ориентир секунды на 10 млн (факт бизнеса, architecture.md §4.5) | App timing / SQL | Разбор запроса, индексы FTS | 2 / 3.1 |
| S3 | Lag курсора watermark (p95) | ≤ 5 мин (Gate A) | SyncState + логи воркера | 2.7.6 | 2+ |
| S4 | Успешность цикла сверки удалений | Цикл выполняется по расписанию | Лог reconciliation | 2.7.7 | до 3 |
| S5 | Ошибки persist (write) | Доля 5xx/SQL ошибок < порога (задать в вехе 7) | Лог CQRS | Доменный toggle / rollback UI | 7+ |
| S6 | Ошибки Excel import | Партиальный успех + отчёт; массовый fail → алерт | Лог Import | Runbook повторной загрузки | 8+ |
| S7 | Память / сессии Blazor | Нет деградации при пике ~100 (факт 2); порог алерта — задать | Perf counters | 2.7.8 / 2.7.11 | 2+ |

#### Уже подтверждённые факты (не путать с полным SLI-фреймворком)

- 100 сессий: ~3% CPU, ~1,5 МБ/circuit (веха 2).
- Sync 200К: ~30 сек, SQL CPU ~15%.
- Бизнес: грид 10 млн — 0,5–3 сек (однопользовательский); выгрузка 120К — 2% CPU / 150 МБ.

Полный протокол нагрузки — приложение D-PERF / backlog 3.1.

Алерты S3/S4/S7 → существующий мониторинг (2.7.8). Без 2.7.8 контракт 98,5% формально
не исполним техподдержкой для новых сценариев [risks.md](risks.md), раздел «Новые сценарии недоступности».

**Критерий готовности:** пороги S5/S6/S7 численно зафиксированы; каждый SLI имеет дашборд/запрос
и владельца реакции.

### Приложение D-MET — метрики продуктивности пилотов

> Статус: **шаблон** (митигация D-MET / условие №7 architecture review; 1.7.4).  
> Первый обязательный замер — пилот вехи 7; далее 8 и первый домен 9.

Условие №7 ревью требует **4 показателя** на пилот. Сейчас есть «2 модели ИИ + факт» и пороги
дефектов; не хватает явной доли ревью и переделок (review/rework). Шаблон закрывает пробел без
единой «магической» цифры ускорения на всю программу (см. 1.7, D-EST).

#### Показатели (обязательные)

| # | Показатель | Как считать | Единица |
|---|------------|-------------|---------|
| 1 | Время человека | Суммарные часы разработчика на пилот (включая ревью и стабилизацию) | чел.-часы |
| 2 | Время агента | Оценка/лог сессий агента на генерацию и итерации (если нет лога — ретроспективная оценка, пометить) | часы |
| 3 | Review / rework | Доля времени человека на code review + переделки после замечаний / дефектов внутреннего теста от показателя 1 | % |
| 4 | Дефекты после приёмки | Critical/Blocker + Major, найденные после UAT/релиза пилота на горизонте стабилизационного окна | штук по severity |

Дополнительно (уже принято): оценка **двух моделей ИИ** до старта + **факт** после выполнения;
