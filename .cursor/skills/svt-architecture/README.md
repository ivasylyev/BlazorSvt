## Почему три, а не одна схема

Целевая архитектура «модульный монолит» может быть развёрнута и на контейнерах, и на классической
ВМ/IIS — это два разных, не взаимоисключающих решения по хостингу. Для бизнеса приоритет —
**бесшовность перехода**, поэтому текущая программа (диаграмма 2) сознательно не меняет
инфраструктуру относительно легаси (диаграмма 1) — меняется только состав и структура ПО.
Переход в контейнеры (диаграмма 3) технически возможен позже, независимо от этой программы, и
не блокирует и не откладывает её результаты. Явное разделение снимает вопрос архитектора
«почему план не доходит до конечного состояния на диаграмме» — потому что диаграмма 3 не является
целью текущей программы.

Единственное, на что диаграмма 3 влияет уже сейчас: выбор механизма сессий Blazor Server
(sticky/affinity, см. `reference.md` §6.1) не должен архитектурно исключать последующий переход
на многоузловой/K8s-деплой.
