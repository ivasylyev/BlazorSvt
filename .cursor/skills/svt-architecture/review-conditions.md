# Условия условного архитектурного одобрения

## Отложенная митигация рисков (условия условного архитектурного одобрения)

**Статус согласования, на которое претендует документация:** условное одобрение
направления трансформации и программы пилотирования — **не** безусловное закрытие
всех нефункциональных требований (NFR) и не разрешение массового тиража / контура записи «как есть».

**Принцип.** Жёлтые зоны повторного архитектурного ревью (architecture review)
(`docs/output-review-package/review-current-state.html`, условия 3–7) — не скрытые пробелы,
а **осознанный остаточный риск (residual risk)** с владельцем, сроком (Gate / веха) и проверяемым
критерием «стало зелёным». Документация не выдаёт план за факт: закрытие условия —
либо **артефакт** (анализ/согласование), либо **исполнение** (код/CI/замер/drill).

Краткая формулировка для пакета ревью — §6.9 в этом файле.
Полный текст документных митигаций (тип A) — **приложения в [mitigations.md](mitigations.md)**
(не отдельные файлы): удобнее для человека-ревьюера.

**Что одобряется сейчас (при принятии условий ниже):**
- направление: модульный монолит Blazor Server + MS SQL FTS, поэтапная замена (Strangler Fig), CQRS,
  Gate A/B/C/D: на Gate C новый контур — источник истины, запись в легаси до Gate D;
- продолжение read-only dual-run и развитие каркаса в рамках уже сделанной вехи 2;
- план работ и реестр отложенных митигаций как обязательная часть программы.

**Что явно не одобряется «вперёд» этим же решением:**
- старт массового тиража оставшихся read-only (backlog 3 / веха 3; 10 RO уже на проде, на тираж — 51 из 61) — до закрытия D-PERF
  (минимум 3.1.10) и D-ARCH (3.2.6);
- пилот записи / загрузчик (веха 7–8) — до закрытия D-SEC-RO (3.2.7) и наличия
  черновиков D-SEC-TM / D-SEC-SOD / D-DATA-MIG (приложения в [mitigations.md](mitigations.md); формальное согласование ИБ —
  по D-SEC-RO и вехе раздела 9);
- единый коэффициент ускорения ИИ в бюджете программы — до калибровки 1.7 (D-EST).

### Правило обновления статуса

При закрытии митигации: в таблице выше меняется формулировка пробела на «закрыто (дата, ссылка
на приложение/протокол)». После этого пакет для ревью пересобирают скриптом
`docs/output-review-package/Build-ReviewPackage.ps1` (zip рядом с папкой; сгенерированные копии скрипт удаляет; zip в git не коммитится).
Повторный architecture review должен видеть трассировку: условие HTML ↔ ID D-* ↔ Gate ↔ приложения в [mitigations.md](mitigations.md).

### 6.9 Условное архитектурное одобрение

Документация претендует на **условное** согласование направления трансформации и программы
пилотирования, а не на безусловное закрытие всех условий повторного architecture review.

**Одобряется при условиях:**
1. Направление (модульный монолит, SQL-only FTS, поэтапная замена (Strangler Fig), CQRS,
   Gate A/B/C/D) признаётся целевым для текущей программы.
2. Жёлтые зоны условий 3–7 ревью ведутся как **отложенная митигация** с проверяемыми критериями
   закрытия — канонический реестр и полный текст приложений (модель угроз (threat model),
   разделение обязанностей (SoD), SLI/SLO, миграции, метрики пилотов, протокол нагрузки):
   этот файл (ID D-PERF … D-DUAL); приложения — [mitigations.md](mitigations.md). Отдельный файл на каждый артефакт D-* не ведётся.
3. Массовый тираж read-only (веха 3 / backlog 3) и контур записи (вехи 7) **не** считаются
   разрешёнными этим же решением, пока не закрыты соответствующие строки реестра в этом файле
   (как минимум D-PERF, D-ARCH, D-SEC-RO для тиража; D-DATA-MIG и артефакты ИБ — для записи).
4. В бюджет программы **не** закладывается единый коэффициент ускорения ИИ до выполнения
   калибровки 1.7 (D-EST); точечные примеры бизнеса по отчётам (§4.5) не подменяют калибровку.

**Зачем так:** остаточные риски (residual risk) не «под ковром», а связаны с Gate и текстом
в этом файле. Закрытие риска = артефакт (приложение) или факт исполнения, не
переформулировка текста. Снимок повторного ревью — `docs/output-review-package/review-current-state.html`.
