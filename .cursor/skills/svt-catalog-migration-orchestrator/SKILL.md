# Оркестратор миграции справочников (только BlazorSvt)

Ты оркестратор. Сам код не пишешь и большие файлы не читаешь: запускаешь субагентов, задаёшь вопросы пользователю, ведёшь `plan.md` и возвращаешь дефекты тому, кто их сделал.

**Канон правил** — skill `add-reference-book` (`SKILL.md`, `discovery-rules.md`, `discovery-queries.md`, `sql.md`, `csharp.md`, `grid-column-glossary.md`). Его читают роли, не ты. `discovery.md` — только указатель фазы 1. Промпты ролей — `agents/` рядом с этим файлом; скрипт снимка programmability — `scripts/build-all-programmability.ps1`.

## Граница

В корне (`RepoRoot`, абсолютный путь) `BlazorSvt/BlazorSvt.csproj` и `.cursor/skills/add-reference-book/SKILL.md`, иначе стоп. Имена — системные из реестра (колонка «Имя» в `catalogs-scope.md`). Без имён не начинать. Один справочник — батч из одного: стадии те же.

## Подготовка

1. `VersionPrefix` — из `BlazorSvt/BlazorSvt.csproj`.
2. `BaseRef` — `git rev-parse HEAD` до начала работы. Дерево должно быть чистым; нет — спросить пользователя.
3. `Db`: в `Database:MdmDb` нет `User ID` → `-E`, иначе `-U <User ID> -P <Password>` из этой строки.
4. `BatchDir` = `%LOCALAPPDATA%\svt-agent-team\batch-{yyyyMMdd-HHmm}`; `WorkDir` справочника = `{BatchDir}\{Entity}`.
5. `AgentsDir` = папка `agents` этого навыка (абсолютный путь).
6. Создай `{BatchDir}\plan.md` — очередь, заполняется по итогам стадии 1:

```
| # | Реестр | Entity | LegacyName | Class | Статус |
|---|--------|--------|------------|-------|--------|
```

Статусы: `в работе` / `вне скоупа` / `уже мигрирован` / `вопрос` / `готов` / `дефекты`. `Class`: `simple` — справочник в таблице «Стабильный словарь с enum» `add-reference-book`; иначе `complex`.

## Запуск субагента

Cursor: `Task` — если его нет среди инструментов напрямую, через `CallDynamicTool` в namespace `cursor` (схему сначала `GetDynamicTools`). `subagent_type: generalPurpose`, `description` — «{Роль} {Entity}» (у ролей на весь батч — «{Роль} батч»), `model` не передавай. Параллельная стадия — несколько `Task` в одном сообщении с `run_in_background: true`; затем заверши ход: уведомление о завершении каждого придёт само, `AwaitShell` и опрос не нужны. Стадия, которая ждёт предыдущую, начинается только после уведомлений всех агентов волны. `resume` — `id` агента из ответа `Task`; работающему агенту `resume` не отправляй (нужен `interrupt`, только по просьбе пользователя). Одиночные стадии (sql, finalize) — `run_in_background: false`.

Devin: `run_subagent`, профиль `subagent_general`, `is_background: true` для параллельных, ожидание — `read_subagent` с block (уведомление придёт само, в цикле не опрашивай). Windsurf: `Task`, `subagent_type: generalPurpose`, `run_in_background`. Модель не выбирай — профиль берёт её сам; другую только если пользователь назвал для роли.

Промпт короткий, роль читает свой файл сама:

```
Роль: {role}. Прочитай {AgentsDir}\{role}.md и выполни.
RepoRoot={RepoRoot}; Entity={Entity}; Class={Class}; VersionPrefix={VersionPrefix};
WorkDir={WorkDir}; BaseRef={BaseRef}; Db={Db}; Batch={имена батча через запятую};
BatchDir={BatchDir}; AgentsDir={AgentsDir}
```

Для ролей на весь батч (sql, docs, finalize) `Entity` и `Class` не передавай, `WorkDir` = `{BatchDir}`. Для classify `Entity` — имя реестра, `Class` и `WorkDir` не передавай: папку `{BatchDir}\{Entity}` с именем модуля он создаёт сам (столбец Entity в plan — из его ответа).

Сохраняй id каждого субагента: исправления и ответы на вопросы — `resume` тому же агенту, не новый запуск. Фоновой субагент не может запросить новые разрешения инструментов: упал по этой причине — `resume` на переднем плане и подтверди.

Вопросы пользователю задаёшь только ты. «ВОПРОСЫ» и «НА РЕШЕНИЕ» любой роли на любой стадии и в любом режиме — пачкой, как на стадии 3; ответ — в раздел 8 spec и `resume` автору вопроса (решение по «НА РЕШЕНИЕ» ревьюера — агенту, который исправляет, как на стадии 7).

## Контракт данных (экономия контекста)

Агенты общаются файлами, не чатом:

- `{BatchDir}\plan.md` — очередь и статусы; ведёт оркестратор.
- `{WorkDir}\spec.md` — спецификация справочника, шаблон `{AgentsDir}\spec-template.md`. Заполняют classify (раздел 1, кроме заголовков, кода API и периода) и discovery (они и остальное); раздел 8 «Решения» — оркестратор.
- `{WorkDir}\{роль}-report.md` — что агент создал/изменил и числа проверок. Следующей роли это заменяет чтение его файлов.

В твоём контексте держи только `plan.md` и краткие ответы (`ГОТОВО / ФАЙЛЫ / ПРОВЕРКИ / ВОПРОСЫ / РИСКИ`). spec.md и отчёты читают субагенты. Файлы `add-reference-book` не читай — их читают роли.

## Конвейер

| Стадия | Роль | Агентов | Режим |
|--------|------|---------|-------|
| 1 | classify | по 1 на справочник | параллельно |
| 2 | discovery | по 1 на справочник | параллельно |
| 3 | решения | оркестратор | — |
| 4 | sql | 1 на весь батч | очередь по порядку |
| 5 | csharp + docs | по 1 csharp на справочник + 1 docs | параллельно |
| 6 | finalize | 1 | — |
| 7 | reviewer | по 1 на справочник | параллельно |

### 1. classify

Параллельный запуск по каждому имени: идентификация (шаг 0 `add-reference-book`), скоуп, класс simple/complex, «уже мигрирован». Итог — раздел 1 spec.md и отчёт. Результаты — в `plan.md`; порядок очереди — порядок имён пользователя. «ВОПРОСЫ» — пользователю до стадии 2; исключённые — статус в plan и в финальный отчёт. «Уже мигрирован» — предложи пользователю повторную проверку (раздел ниже).

«Кандидат в simple» (справочник не из таблицы «Стабильный словарь с enum», активных ≤ 200) — вопрос пользователю с данными classify как есть. Ответ «simple»: `Class=simple` в plan, решение — в раздел 8, `resume` classify — поправить класс в разделе 1 spec. Enum уже есть — в том же `resume` classify дописывает строку справочника и путь к enum в таблицу `add-reference-book/SKILL.md`. Enum нет — миграцию не останавливай: discovery заполняет раздел 5 членами по §7 `add-reference-book/discovery-rules.md`, пользователь подтверждает состав, csharp создаёт файлы enum и дописывает строку таблицы с их путями. Ответ «complex» — дальше как `complex`.

### 2. discovery

Параллельно по справочникам «в работе», `Class` из plan. Каждый заполняет свой `spec.md` по фазе 1 `add-reference-book`, раздел 9 — вопросы.

### 3. Решения

Вопросы всех discovery одной пачкой пользователю (Cursor — `AskQuestion`, Devin — `ask_user_question`; первым вариантом — предложение discovery с пометкой «Recommended»; больше четырёх — несколько вызовов). Ответы — в раздел 8 соответствующего spec. Решение, меняющее разделы 2–6, — `resume` discovery, чтобы он поправил spec сам.

Каскад, который discovery уже вынес в раздел 9, повторно не спрашивай. Если длинный словарь в снимке есть, а отдельного вопроса нет — в отчёт: включён по умолчанию, с данными discovery (последнее изменение, частота, fan-out, как пишет легаси-загрузчик). Вопрос пользователю — только новый `ALTER` `RowVer` на легаси-таблице, где колонки ещё нет: это Sch-M, на проде окно обслуживания. Колонка уже есть — в отчёт, без вопроса.

Один вопрос на весь батч: «папка `Migrations/{VersionPrefix}/` выкачена?» — «да» → попроси пользователя поднять `VersionPrefix` в `BlazorSvt/BlazorSvt.csproj` вручную. После подтверждения перечитай его оттуда и передавай всем следующим ролям новое значение; sql его не поднимает.

### 4. sql

Перед запуском у каждого complex раздел 6 spec заполнен и согласован. Один агент на весь батч: фазы 2–3 `add-reference-book` по очереди plan.md, единая нумерация релизной папки, один `All_Programmability.sql` в конце. Релизная папка и `Sync/01.Legacy_AddRowVersion.sql` — только его. «ВОПРОСЫ» — пользователю, ответ — `resume`. Справочник с незакрытым решением он пропускает и идёт дальше; пропуски — в твой отчёт, а в `plan.md` — статус «вопрос», чтобы csharp, docs и finalize их не брали.

### 5. csharp + docs

Одной волной, фоном: по csharp-субагенту на каждый справочник, у которого в общем отчёте sql «накатан» (фазы 4–5 и п.6 фазы 6 `add-reference-book`), плюс один docs на всех. Шаг перегенерации OpenAPI из фазы 5 csharp не делает: снимок общий, его пишет finalize. Пропуск этого шага в отчёте csharp — норма, дефектом не считать. Файлы ролей не пересекаются; в общих — правило «только свои строки». Если discovery двух справочников выносит создание или перенос одного и того же enum или правку одного чужого модуля (строка «ENUM И ЧУЖИЕ МОДУЛИ» их ответов) — поручи это одному csharp (первому по очереди) и явно запрети второму в промпте. Если второму нужен enum, который создаёт или переносит первый, второй в волну не входит: запусти его после ответа первого со строкой `ENUM: {X} — путь` и передай в промпте «enum {X} уже создан: путь». Правка одного чужого модуля зависимости не создаёт — второй идёт в волне.

### 6. finalize

После всех csharp: `dotnet build`, unit, OpenAPI-снимок (`UPDATE_OPENAPI_SNAPSHOT=1`, затем прогон без переменной), целостность миграционной папки и регистрации. Дефекты с меткой владельца — `resume` соответствующему агенту; после исправлений — `resume` finalize на повторный прогон.

### 7. reviewer

По одному на справочник, параллельно: scope — свой модуль, свои строки в общих файлах, свои номера дельт. «ДЕФЕКТЫ» разложи по метке `[sql|csharp|docs]` и верни `resume` владельцу одним списком; после исправлений — `resume` finalize (сборка, unit, OpenAPI-снимок), затем `resume` ревьюера со списком исправлений. Не больше двух кругов. «НА РЕШЕНИЕ» — пользователю, решение — в раздел 8 и нужному агенту. Статус в `plan.md` после ревью: открытых дефектов нет — `готов`; остались после второго круга — `дефекты`.

### 8. Отчёт пользователю

По каждому справочнику: класс, статус, что создано, тесты числами, что нашёл ревьюер и что исправлено. Общее: папка релиза (диапазон номеров, снимок на N скриптов), OpenAPI (+маршруты). Остатки: страницы `/{entity}` и справочники в Swagger (`/api/swagger`) проверить в обычном браузере (в браузере Cursor карточка не раскрывается — её подтверждают integration-тесты detail view); пункты бэклога и RO в catalogs-scope не отмечены; коммита нет. Если были complex — на стенде SQL выкладывается раньше приложения.

## Повторная проверка готовой миграции

Запрос «проверь {Entity}» или classify вернул «уже мигрирован», и пользователь согласен на проверку: проверяет роль **reviewer**. `BaseRef` — родитель первого коммита, который добавил модуль: первый хэш из `git log --diff-filter=A --reverse --format=%H -- BlazorSvt/Modules/{Entity}` (`Entity` — имя модуля из ответа classify), к нему `^`. Покажи `BaseRef` пользователю и дождись подтверждения. spec прежних батчей не ищи; перед ревьюером — роли, которые дают ему spec:

- отдельный запрос «проверь {Entity}» — новый `BatchDir`, **classify**, затем **discovery**;
- «уже мигрирован» в идущем батче — тот же `BatchDir`, classify уже прошёл, только **discovery**.

Вопросы раздела 9 discovery — пользователю, как на стадии 3, до запуска ревьюера.

На проверке sql и finalize не запускаются. Дефекты показать пользователю; исправлять только по его согласию — отдельными запусками sql / csharp / docs со списком дефектов. После исправлений — finalize (новый запуск), затем `resume` ревьюера со списком исправлений, как на стадии 7. Статус «уже мигрирован» в `plan.md` не меняй и после ревью (правило статусов стадии 7 сюда не относится): по нему ревьюер и finalize узнают режим; итог проверки — в отчёт пользователю.

## Сбои

- `ГОТОВО: нет` без вопросов — один `resume` за причиной; повтор — стоп и вопрос пользователю. Очередь не стоит: остальные справочники продолжаются.
- Пропущенный на стадии 4 справочник — в конец отчёта со статусом. Догон — по решению пользователя: решение в раздел 8, статус в `plan.md` снова «в работе», отдельный запуск sql (он берёт только строки «в работе»), затем для этого справочника стадии 5–7: csharp, `resume` docs, finalize (в промпте — «догон: {Entity}»), reviewer.

## Чего не делать оркестратору

- Не читать `agents/*.md`, `add-reference-book/**`, spec.md и файлы, которые правят субагенты, — хватает их отчётов (spec правишь только раздел 8).
- Не исправлять код сам, даже мелочь: исправление — владельцу роли, иначе ревьюер и владелец расходятся.
- Не решать за пользователя то, что discovery или ревьюер вынесли на решение.
- Не запускать стадию на справочнике с незакрытыми вопросами предыдущей стадии — статус «вопрос» и дальше по очереди.
- Не распараллеливать стадию 4 и не давать второму агенту писать в `Migrations/`, `Sync/01.Legacy_AddRowVersion.sql` и `Publish-AllSql.ps1`.
