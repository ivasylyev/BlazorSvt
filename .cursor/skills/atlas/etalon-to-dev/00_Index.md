# Индекс пакетов для анализа логов

Рабочий файл лидера цифровизации от ИТ. Здесь три вещи: карта пакетов с ожиданием по логам, единая структура черновика и порядок работы.

## 1. Пакеты и ожидание по логам

Колонка «логи» — ожидание до приёмки данных, гипотеза из эталона. Она уточняется на этапе «Приёмка» (Промпт 2а, этап 1) и заменяется светофором по фиксированным критериям (этап 4.2).

| Пакет | Есть ли логи (ожидание) | На основании чего собран |
|---|---|---|
| Ш1 · Регистрация сигнала | частично — журналы проводок и закрытия учётного контура; почта следов не оставляет | раздел 3 эталона, строка Ш1; приложения 1–3 |
| Ш2 · Квалификация и материальность | нет — существенность решается суждением, следы в переписке | раздел 3, строка Ш2; приложения 1–3 |
| Ш3 · Экономическая диагностика | частично — окна BI и таблиц в следах рабочих мест; сами разложения в файлах | раздел 3, строка Ш3; приложения 1–3 |
| Ш4 · Пересчёт прогноза | частично — журнал версий инструмента планирования, если ведётся | раздел 3, строка Ш4; приложения 1–3 |
| Ш5 · Выработка реакции | нет — варианты готовятся в таблицах и презентациях | раздел 3, строка Ш5; приложения 1–3 |
| Ш6 · Принятие решения | частично — журнал изменения лимитов; протоколы комитетов — документы, не события | раздел 3, строка Ш6; приложения 1–3 |
| Ш7 · Передача в кольца-заказчики | частично — журналы изменений лимитов и справочников; подтверждения в письмах | раздел 3, строка Ш7; приложения 1–3 |
| Ш8 · Закрытие фактом и оценка | нет — акта закрытия сегодня не существует, значит нет и его следов | раздел 3, строка Ш8; приложения 1–3 |
| Сквозные механизмы П1–П6 | частично — справочники, версии планов, журналы изменений | раздел 3.1; приложения 1–3 |
| Интеграции | не по логам — по документации и интервью с техвладельцами систем | разделы 1.3 и 2 эталона |

## 2. Структура черновика — единая для всех пакетов

Черновик `Черновик_<код пакета>.md` повторяет структуру шаблона владельца (раздел 6 Промпта 2):

1. **Паспорт** — границы, наблюдаемая картина исполнения, объёмы и частоты из данных.
2. **Реестр релевантных данных** — код / название / источник сегодня / способ доступа / пример значения.
3. **Карточка на каждого агента пакета** — текущий аналог, триггер и вход, логика решения, границы и точка передачи человеку, событие-результат, примеры (типовые, граничные, случаи передачи человеку), метрика качества.
4. **Реестр релевантных контролей** — код / что проверяет / условие / где проверяется сегодня.

В шапке каждого черновика: период данных, светофор пакета, три главных ограничения (глубина следов рабочих мест, наличие объектных идентификаторов, консистентность маскировки). Целевые формулировки эталона в черновик не переносятся. Когда Промпт 2а на этапе «Раскладка» (раздел 4.3) запрашивает «структуру, которую требует промпт этого пакета» — структурой служит этот раздел, один на все пакеты.

## 3. Порядок работы

1. Единая событийная база строится **один раз по всему массиву логов** — этапы 1–3 Промпта 2а (приёмка → база → связность). Не по пакету за раз.
2. Раскладка по пакетам начинается только на этапе 4: Промпт 2а прогоняется по каждому пакету **поверх готовой базы**, создаёт `Черновик_<пакет>.md`.
3. Черновик уходит владельцу по маршруту раздела 6 Промпта 2: черновик → шаблон владельца, владелец переносит и правит.
4. После заполнения шаблонов по **той же базе** прогоняется сверка «сказанное против фактического» (Промпт 2а, раздел 5) — пересборка базы с нуля не требуется.
