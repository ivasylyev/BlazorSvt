# Промпт 2а: обработка логов — от сырых архивов до черновиков пакетов

---

## 0. Железные правила (действуют весь диалог, наследуются всеми результатами)

1. **Хэши не деанонимизируются.** Если в пакете есть файл-маппинг «маска → реальный логин» — зафиксировать его существование как риск в паспорте данных; открывать его можно только чтобы посчитать число строк и понять формат; использовать для раскрытия конкретных людей — запрещено. Выводы — на уровне ролей и групп. Минимальная группа для любой цифры по людям — 5 человек; если в разрезе меньше 5 — писать «наблюдаемая группа ≤5 учёток», без имён, логинов и хэшей.
2. **Каждая цифра — с источником.** Формат обязателен: `<число> (источник: <файл или таблица>, период <даты>, метод: <как посчитано>)`. Цифра без источника не существует. «Примерно», «около», «много» без вычисления — запрещены; если посчитать нельзя, пиши «не вычислимо, причина: …».
3. **Пометки достоверности на каждом утверждении:** `[факт из лога]` — прямое наблюдение (можно ткнуть в строки файла); `[вывод]` — расчёт или сопоставление, формула/логика написана рядом; `[гипотеза]` — интерпретация, которую должен подтвердить владелец; `[нет данных]` — следа нет. Утверждение без пометки — ошибка.
4. **Не сглаживать и не досочинять.** Пустой файл, битый архив, лог вне запрошенного периода, система без событий, расхождение двух источников — это результаты, их фиксируют, а не «чинят» и не замалчивают. «В логах не видно — вопрос владельцу» — валидный и частый ответ. Придуманный правдоподобный ответ — грубейшая ошибка, обесценивающая всю работу.
5. **Семантику непрозрачных полей не угадывать.** Код действия без легенды остаётся кодом (`user_action=13`, `EVENT_CODE=4003`). Смысл — только с пометкой `[гипотеза]` и объяснением, из какого контекста гипотеза взята. Запрос легенды — в список дозапросов.
6. **Периметр пакета соблюдать.** При раскладке по шагам (этап 4) операция чужого шага отмечается строкой в списке «непокрытые операции» — и не анализируется.
7. **Имена файлов — не источник истины.** Период, состав, система определяются по содержимому, не по названию файла. Файл «2026-01.csv» может содержать март.
8. **Ничего не удалять и не править в исходных данных.** Все преобразования — в копиях/производных файлах.

## 1. Этап «Приёмка»: инвентаризация до какого-либо анализа

Цель: полная опись пакета. Анализировать содержимое на этом этапе запрещено — только описывать.

### 1.1. Распаковка

- Раскрывать архивы **рекурсивно**: архив внутри архива — норма (zip в 7z в zip). Продолжать, пока не останется ни одного нераспакованного архива.
- Вести **журнал распаковки** — таблицу: `архив | вложен в | статус (распакован / требует пароль / битый) | что внутри (число файлов)`.
- Запароленные архивы: собрать в один список и запросить пароли у оператора **одним сообщением**, продолжая работу с остальным. Не ждать ответа, не останавливать этап. Полученный пароль пробовать на все запароленные архивы, не только на один.
- Битые архивы: попытаться распаковать дважды (вторая попытка — другим инструментом/с игнорированием ошибок), после второй неудачи — в журнал со статусом «битый», работа продолжается.
- Файлы нулевой или почти нулевой длины (только строка заголовка): отдельный список «пустые файлы». Это не мусор — это пользователи/системы без событий, находка сама по себе.

### 1.2. Опись каждого файла

По **каждому** файлу пакета (включая пустые) — строка инвентарной таблицы:

```
| Путь | Размер | Формат | Кодировка | Разделитель | Строк | Колонки (первые 10–15) | Пример 1–2 строк данных |
```

Правила определения:

- **Кодировку** определять пробой в порядке: utf-8-sig → utf-8 → cp1251 → utf-16. Русские логи часто в cp1251; BOM в начале — признак utf-8-sig. Если текст читается «кракозябрами» — кодировка определена неверно, пробуй следующую.
- **Разделитель** определять по первой строке: посчитать в ней количество `,` `;` `\t` `|` — разделитель тот, которого больше. Не предполагать запятую по умолчанию: `;` в русских выгрузках встречается чаще.
- **Число строк** считать честно (по файлу), не оценивать на глаз.
- Для xlsx: перечислить **все листы**, по каждому — размерность и заголовки. Первый лист — не всегда данные (бывает лист-шапка отчёта, лист «SQL»).
- Для json: определить структуру (массив объектов / объект-на-строку NDJSON / вложенный) и перечислить ключи первого уровня.

### 1.3. Пять определений по каждому источнику

Для каждого источника (система/выгрузка, может состоять из многих файлов) определить и записать в паспорт:

1. **Период данных**: `min` и `max` отметки времени **из содержимого**. Если колонок времени несколько — какая из них событийная. Если дата замаскирована или в нестандартном формате — так и записать.
2. **Ключ пользователя**: реальный логин / маскированный токен / отсутствует. Привести пример значения.
3. **Ключ объекта**: есть ли ID документа/заявки/карточки/наряда, по которому события группируются в историю одного экземпляра. Это самое важное поле описи: от него зависит, будут ли трейсы. Привести пример.
4. **Тип журнала**: *событийный* (строка = действие пользователя над объектом) / *технический* (журнал регистрации, серверный лог — бизнес-семантика не извлекается) / *справочный* (список пользователей, объектов, соответствий).
5. **Особенности парсинга**: многострочные поля в кавычках, маскированные даты, шапка-отчёт перед данными, отсутствие заголовков, «весь лог в одной колонке», нестандартный формат дат — всё, что сломает наивный парсер.

### 1.4. Кросс-проверка маскировки

Если пользователи замаскированы токенами: взять два крупнейших источника с токенами, построить множества уникальных токенов, посчитать пересечение. Записать буквально: «источник А: N токенов, источник Б: M токенов, общих: K». K > 0 и правдоподобно — маскировка консистентна, источники сшиваются по токену; K = 0 — сшивка невозможна, писать прямо. Не заявлять консистентность без этой проверки.

### 1.5. «Обещано → фактически»

Если есть README/сопроводительное письмо/спецификация пакета — таблица:

```
| Обещано | Фактически получено | Расхождение |
```

Типовые строки: кадровый справочник ролей; глубина истории (месяцев); синхронный срез; коммуникации; перечень систем. Таблица обязательна, даже если всё совпало (тогда колонка «Расхождение» из «нет»).

### 1.6. Артефакт этапа — «Паспорт данных»

Один документ: журнал распаковки, инвентарная таблица, пять определений по каждому источнику, список пустых файлов, список систем без логов, вердикт по маскировке, таблица «обещано → фактически», список запароленного/битого.

**Проверь себя перед этапом 2:** описаны 100% файлов, включая пустые и битые? у каждого источника заполнены все пять определений? проверка маскировки сделана пересечением множеств, а не предположением? Если хоть один ответ «нет» — этап не закончен.

## 2. Этап «База»: единая событийная база

Цель: превратить разнородные файлы в структуры, по которым можно считать. Если среда позволяет выполнять код — использовать колоночное хранилище (parquet + DuckDB или эквивалент); миллионы строк текстом не обсчитываются. Если код недоступен — работать по тем же правилам на выборках, но каждый раз писать: «посчитано по выборке N строк из M, полный расчёт требует среды с выполнением кода».

### 2.1. Ядро — лог агента task mining (если есть)

- Привести к схеме: `время · пользователь · сессия · приложение · окно · тип_события · длительность_мс`.
- Первым делом проверить, **какие поля реально заполнены**. Типовой случай: поля уровня контролов (control_id, action, элемент формы) существуют в схеме, но пусты во всём массиве. Тогда записать ограничение метода: «восстановимы окна приложений и переключения между ними; действия внутри форм — нет». Это ограничение обязано попасть во все черновики.
- Посчитать и записать: всего событий, уникальных пользователей, период, распределение по типам событий (окно/простой), суммарные часы по каждому типу.

### 2.2. Расшифровка маскированных имён приложений

Если имена приложений замаскированы токенами — вскрывать по заголовкам окон. Процедура: для каждого токена взять топ-20 самых частых заголовков окон и искать сигнатуры:

- «Входящие», «— Сообщение (HTML)», «Напоминаний» → Outlook;
- «Книга1», «Найти и заменить», «Сохранение документа» + имена .xlsx → Excel;
- «Документ1», «Абзац» → Word; «Презентация1» → PowerPoint;
- хвост «— Microsoft Edge» / «— Google Chrome» → браузер;
- «проводник», «Этот компьютер» → Проводник.

Результат — таблица «токен → приложение → 2–3 заголовка-доказательства», каждая строка с пометкой `[вывод]`. Токен, который не удалось расшифровать, остаётся токеном — в таблицу со статусом «не расшифрован».

### 2.3. Классификация окон браузера по системам

Веб-системы живут внутри одного процесса браузера — относить окно к системе по ключевым словам заголовка (название системы, характерные экраны). Правила:

- Список слов-классификаторов выписать **явно** (он попадает в паспорт данных): `система X ← слова: «…», «…»`.
- Окна, не попавшие ни в одну систему, — категория «прочее». Её объём (событий, часов) назвать честно. Если «прочее» больше любой системы — сказать это прямо, не прятать.
- Не относить окно к системе по догадке: нет ключевого слова — значит «прочее».

### 2.4. Событийные журналы систем

Каждый привести к общей форме `время · пользователь · система · действие · объект (если есть)` — отдельным парсером на источник, с учётом особенностей из описи (п. 1.3.5). Ошибки парсинга не глотать: строка не распарсилась — счётчик ошибок по источнику, в паспорт.

### 2.5. Артефакты этапа

1. **Сводка по системам**: `система | событий | пользователей | часов (если применимо) | период`.
2. **Сводка по времени**: события по месяцам по каждому крупному источнику — таблицей. Дыры в периодах видны именно здесь; каждую дыру назвать.
3. **Словарь действий** по каждому событийному журналу: топ-20 кодов/действий с частотами. Коды без легенды — остаются кодами (правило 0.5).

**Проверь себя перед этапом 3:** суммы строк в базе сходятся с описью (±ошибки парсинга, посчитанные)? таблица расшифровки токенов приложений построена и в ней нет строк без доказательств? объём категории «прочее» назван числом?

## 3. Этап «Связность»: переходы, разрывы, трейсы

### 3.1. Матрица переходов между системами

Алгоритм — буквально, без творчества:

1. Взять события типа «окно» с непустой классификацией (система или офисное приложение).
2. Разбить по пользователю и календарному дню; внутри каждой группы отсортировать по времени.
3. Для каждой пары соседних событий с **разными** классификациями записать переход `откуда → куда`. Переход через границу дня не считается.
4. Агрегировать: `откуда | куда | число переходов | уникальных пользователей`.

Отчёт в двух разрезах, отдельно: **(а)** прямые перескоки бизнес-система → бизнес-система; **(б)** переходы с участием офисного слоя (почта, файловый менеджер, Excel, мессенджеры). Соотношение (а) и (б) — обязательный вывод: оно показывает, идёт ли маршрут процесса через интеграции или через почту и Excel.

### 3.2. Разрывы через Excel

Цепочки «система → Excel → та же система» в пределах пользователя и дня: тройки соседних классифицированных событий, где первое и третье — одна система, среднее — Excel. Выдать: число цепочек, число затронутых пользователей, топ систем по числу цепочек. Это заготовка ответа «где ручные мосты» для по-пакетных промптов.

### 3.3. Трейсы объектов

Там, где журнал имеет ключ объекта (п. 1.3.3):

1. Сгруппировать события по объекту, внутри — отсортировать по времени.
2. Склеить последовательность действий в строку-вариант: `создан → согласован → … `.
3. Посчитать: частоту каждого варианта (топ-10), число объектов всего, долю дошедших до финального состояния (если финал определим), медианную длительность от первого до последнего события.
4. Если финальное состояние неопределимо (коды без легенды) — писать: «завершённость не определима, причина: …».

Где ключа объекта нет — писать прямо: «маршруты экземпляров невосстановимы, доступна только интенсивность работы», и внести пообъектную выгрузку в дозапросы.

### 3.4. Кросс-системная сшивка объектов

Поискать общие ID между системами: значения объектных полей одной системы в полях другой (по формату и по пересечению множеств значений). Найден мост — описать: какие поля, сколько совпадений. Не найден — записать вердикт дословно: «сквозной экземпляр через N систем не собирается; сшивка возможна только по пользователю и времени — это корреляция, не причинность». Этот вердикт обязан попасть во все черновики.

**Проверь себя перед этапом 4:** матрица переходов построена по алгоритму 3.1 (не по памяти о «типичных паттернах»)? для каждой системы с ключом объекта построены трейсы, для каждой без ключа — явная запись о невосстановимости? вердикт по сшивке сформулирован одним предложением?

## 4. Этап «Раскладка»: привязка к кольцу и черновики пакетов

Только теперь открыть эталон (кольцо Ш1…Шn из Промпта 1) и по-пакетные промпты из `4_Инструменты_аналитика`.

### 4.1. Маппинг «система/операция → шаг»

Таблица: `система или операция | шаг кольца | основание | пометка`. Правила:

- Одна система может обслуживать несколько шагов (учётное ядро — почти всегда). Тогда к шагу привязывается **операция/транзакция/экран**, не система целиком.
- Очевидные привязки — `[вывод]` с основанием; спорные — `[гипотеза]` с вопросом владельцу.
- Если два шага в данных неразличимы (одни и те же окна/операции) — писать «шаги X и Y в данных не разделяются», не делить искусственно.
- Системы, не относящиеся к процессу, — отдельным списком «вне контура», с указанием, куда они относятся (сквозные механизмы, другой процесс).

### 4.2. Светофор обеспеченности по каждому шагу

Критерии фиксированные, не интерпретировать:

- **Зелёный** — есть событийный журнал операций шага (действия с отметками времени, желательно с объектами).
- **Жёлтый** — есть только косвенные следы: окна приложений, запуски транзакций без объектов, входы в систему.
- **Красный** — следов нет вообще.

Каждому красному шагу — строка в дозапросах. Красный шаг — не повод молчать: его черновик состоит из записей `[нет данных]`, и это легальный черновик — ненаблюдаемость шага сама по себе вывод, который владелец должен объяснить.

### 4.3. Прогон по-пакетных промптов

По одному пакету за прогон, поверх базы этапов 2–3 — **не поверх сырых файлов**. На каждый пакет — черновик `Черновик_<код пакета>.md` со структурой, которую требует промпт этого пакета (паспорт шага, реестр данных, текущий аналог и baseline по агентам, банк кейсов где возможен, вопросы владельцу). В шапке каждого черновика: период данных, светофор шага, три главных ограничения (глубина task mining, наличие объектных ID, консистентность маскировки).

### 4.4. Единый список дозапросов

Одна таблица на весь пакет данных: `что запросить | какие разделы каких пакетов разблокирует`. Типовые кандидаты: кадровый справочник ролей; пообъектные выгрузки учётной системы (номера документов + истории статусов); журналы этапов процедур; легенды кодов событий; коммуникационные метаданные; недостающие месяцы истории; пароли невскрытых архивов.

**Проверь себя перед выдачей:** у каждого шага кольца есть строка маппинга и светофор? число черновиков равно числу пакетов? в каждом черновике в шапке — период, светофор, ограничения?

## 5. Выход и передача

- **Паспорт данных** — оператору и менеджеру процесса (ответ на вопрос «что нам вообще прислали»).
- **Черновики пакетов** — владельцам, по маршруту Промпта 2 (черновик → шаблон владельца).
- **База этапов 2–3 сохраняется**: промпт сверки («сказанное vs фактическое») прогоняется по ней же — пересборка с нуля не должна требоваться.
- Если анализ вёлся иначе — результаты всё равно оформлять в те же три артефакта: паспорт, база, черновики. Форма важнее пути.

## 6. Чего делать нельзя — типовые ошибки слабых моделей

Каждый пункт — реальная ошибка, которую совершают ИИ на этой задаче. Перед выдачей любого артефакта пройди список и проверь, что не совершил ни одной.

1. **Придумать цифру.** Любое число, которое ты не посчитал по файлам в этой сессии, — не существует. «В среднем в таких компаниях…» — запрещено везде, кроме явного раздела бенчмарков, если его требует формат.
2. **Пересказать вместо посчитать.** «В логе много ошибок» — мусор. «Событие "Произошла ошибка" — 521 из 1 942 строк журнала (27%)» — результат.
3. **Поверить имени файла или README.** Период и состав — только из содержимого (правило 0.7).
4. **Проанализировать выборку и выдать за целое.** Если считал по выборке — размер выборки и оговорка обязаны стоять рядом с каждой цифрой.
5. **Пропустить файлы молча.** Не смог открыть/распарсить — строка в паспорте со статусом и причиной. Число описанных файлов обязано сойтись с числом файлов на диске.
6. **Заполнить пробел правдоподобным текстом.** Пустое поле шаблона с красивой общей фразой хуже, чем честное `[нет данных]`. Проверка: у каждого содержательного утверждения есть источник-файл? Нет — это домысел, удалить.
7. **Раскрыть человека.** Ни одного реального логина, ФИО или хэша в связке с выводом о конкретном человеке. Группа меньше 5 — обезличить до роли/группы (правило 0.1).
8. **Усреднить несовместимое.** Не складывать периоды разной длины, пользователей разных систем, события разных типов в одну «среднюю» цифру без явной формулы.
9. **Переименовать коды.** Коды шагов/агентов/данных берутся из эталона дословно (кириллица: Ш/П/А/К/Д/М/В). Свои обозначения не вводить.
10. **Показать владельцу целевой слой эталона.** В черновики для владельцев целевые формулировки не переносятся (правило Промпта 3: увидев целевой вариант, владелец подстроит ответ).
11. **«Улучшить» метод.** Пропустить инвентаризацию и сразу искать инсайты; нарисовать процесс по здравому смыслу; округлить «для красоты» — всё это ломает воспроизводимость. Этапы выполняются в порядке 1 → 2 → 3 → 4, артефакты выдаются на каждом.
12. **Забыть слово-запрет.** Центр кольца называется «ядро»; слово «ступица» не используется нигде (правило Промпта 1).

## 7. Финальная проверка перед выдачей (отвечать цифрами и да/нет)

- Файлов на диске: N; строк в инвентарной таблице: N. Совпадает?
- Запароленных/битых/пустых: перечислены списками?
- Вердикты по трём фундаментальным вопросам даны, каждый одним предложением: (1) консистентна ли маскировка между источниками; (2) есть ли объектные ID и сшиваются ли системы; (3) какова фактическая глубина task mining — окна или действия?
- Таблица «обещано → фактически» есть (даже если всё совпало)?
- У каждой цифры в каждом артефакте — источник и пометка достоверности?
- Ни одной цифры по группе людей меньше 5?
- У каждого шага кольца — светофор; у каждого красного шага — строка в дозапросах?
- Число черновиков = числу пакетов?
- Список ошибок раздела 6 пройден по пунктам?
