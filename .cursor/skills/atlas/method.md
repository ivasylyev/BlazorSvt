# Метод кольца (Агапов)

Источник: единый промпт «Проектирование эталонного процесса методом кольца», ред. 6 методологии Атласа. Это метод, не интерфейс продукта Атлас.

## Кольцо, не конвейер

Экземпляр проходит обод. Факт возвращается и **переписывает правила**, по которым родится следующий экземпляр. Нет обратной связи — это не кольцо.

Формула каждого шага: **событие → правило → действие**. Правило не зашито в шаг: одно место, все шаги читают.

### Нормальные формы

- **1НФ** — шаг решает одну задачу и даёт одно событие на выходе.
- **2НФ** — нет половинчатого решения на неполных данных: событие «данные неполны» → человек, не догадка.
- **3НФ** — правило в одном месте с одним владельцем. Копия правила у потребителя — ошибка декомпозиции.

### Два слоя

- **Обод Ш1…Шn** — 6–12 этапов экземпляра, от повода до оценки. Больше 12 — укрупнить; меньше 6 — шаг проглочен.
- **Ядро П1…Пm** — 5–10 механизмов, на которые ссылаются несколько шагов (справочники, полномочия, шина событий, очередь людям, аналитика). Слово «ступица» не использовать.

### Три потока

- По часовой — экземпляр.
- Против часовой — обучение (факт → правила ядра).
- Радиально — к человеку, только где решение дорогое, необратимое или окончательное.

Вариации (виды, типы) — **профили В**, не второе кольцо. В профиле назвать, какие шаги пропускаются и какой контроль добавляется.

### Вспомогательный процесс

Ключевой процесс порождает требование, не наоборот. Экземпляр — требование (данные, норматив, мощность). Закрытие — факт из кольца-заказчика. Смена правила заказчика — легальное закрытие. Правила самого вспомогательного домена меняют **вне** оборота экземпляра.

## Коды

На схеме видны **Ш** и **П**. Остальное — расшифровка. В документе словарь кодов — сразу после титула, до первого кода в тексте (кроме случая, когда код вводится после шагов, которые он обозначает).

| Код | Что |
|-----|-----|
| Ш | Шаг обода |
| П | Механизм ядра |
| Ч | Человек (исключение с обода) |
| А | Агент (исполнитель / контролёр) |
| К | Контроль в транзакции: блокировка / маршрутизация / уведомление |
| Д | Элемент данных: один владелец, одно место |
| М | Сквозной индекс процесса, не KPI функции |
| В | Профиль вариации |
| ASM | Допущение, которое надо проверить с владельцами |

Стык со смежным кольцом — **контракт**: что пришло (событие + код источника), что ушло, правило стыка, чей контроль. Коды чужого кольца, если архитектура есть, брать дословно.

Обязательна таблица **«Где в кольце привычные процессы»**. Привычный подпроцесс без места в узле / ядре / профиле / стыке — пробел конструкции.

## Два прохода

Целевое кольцо можно собрать из логики. **Текущее состояние — нельзя.**

**Проход 1.** Целевое целиком. Ячейки «как сейчас» и «сложность» — плейсхолдеры, не выдумки. Колонка «как должно быть» пишется.

**Проход 2.** Заполнение из ответов владельцев, документов пользователя, логов. «Не знаю» валидно. Сложность — цена состояния, не пересказ as-is. Решение закрывает названную сложность один в один.

Три разреза на каждом шаге: документы, интервью, логи. Шаблоны пользователям не рассылать, если на автологистике это не дало пользы.

## Два документа метода

**Документ 1** — целевая архитектура для команды: L1 карта, L2 шаги, L3 сценарии, агенты, контроли, данные, метрики, роли, стыки, допущения.

**Документ 2** — executive: видение кольца, один разбор шага «суждение → правило», стыки, привычные процессы, as-is → сложность → решение.

Для СВТ сейчас живой материал — HTML идеального процесса (аналог эталона логистики для правления). Сам эталон логистики — [logistika-etalon-pravlenie-2-1.html](logistika-etalon-pravlenie-2-1.html) в этом навыке. Полную пару Doc1/Doc2 не собирать, пока пользователь не попросил.

## Роли в методологии

Один раздел «Роли и ответственность» (как §9 эталона логистики): бизнес-лидер, владелец процесса, ИТ-лидер, владельцы шагов/данных. Это контур ведения работы.

Роли **пользователей системы** (кто что правит в UI) и точки **Ч** живут у кольца, не дублируются вторым разделом в хвосте.
